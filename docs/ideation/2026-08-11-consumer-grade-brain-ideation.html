What changed in this revision

The container approach is gone. The previously top-ranked idea — run unmodified gbrain in an ephemeral container and inherit ~96% of its behavior by execution — was rejected: it buys inheritance at the cost of controlling your own codebase. Idea #2 is now a genuinely different mechanism, and its failure mode is the opposite one (quiet decay rather than runtime coupling), so the design is built around measuring the gap rather than eliminating it.

Management surfaces are a new axis. A consumer web app plus an in-chat visual app installable in Claude and ChatGPT. The panel is the primary management surface; the one moment that leaves it is OAuth consent, which opens a real browser tab the way every "Sign in with Google" flow already does — see #3.

Capability parity audit — verdict: not yet

A six-lane audit inventoried gbrain's capabilities from the repo and mapped 131 of them against these nine ideas: 38 critical, 51 outright gaps, 58 partial. Full report in docs/research/2026-08-11-capability-parity.md. The verdict is that the gap is almost entirely in accuracy, not functionality — and the three findings below are the ones that matter.

1. Nothing in these nine cards causes the brain to be read or written at all. gbrain's two most load-bearing behaviors — a signal-detector that fires on every inbound message, and a brain-first rule before answering anything about a person — live in a skills layer this design deleted without replacing the mechanism. The consequence compounds: no writes → no debt → no consolidation → no salience or entity cards → #5's live briefing assembles over an empty materialized layer and #7's upgrade prompt has nothing to count. The available fix costs zero tool names — MCP's server instructions field, which the design never mentions.

2. Answer quality is a ~19-stage post-retrieval pipeline; this design commits to two. Unambiguously committed: RRF fusion and token-budget packing. Half-committed: the vector, keyword and relational arms, and intent classification. Unmentioned: thirteen — including cross-encoder reranking, which reshuffles 60% of top-1 results on a real corpus, and the alias hop, which is the only layer bridging true synonyms with zero surface overlap. Two further traps: the relational arm is worth +31 P@5 (49.1 against ~18 without it), but its typed edges come from LLM extraction, which #7 places below the free-tier line — so the free tier runs the single largest quality lever against an empty graph. And autocut as ported is structurally broken: it reads a rerank score by design, and gbrain measured the RRF-gap alternative at 0.602 versus 0.569 and concluded it is mechanical decay, not signal.

3. Nothing measures answer quality. #2 grades the wire — tool lists, response schemas, error envelopes — and will pass green while write-back drops a fact or a bad extraction prompt degrades every briefing every user reads. There is no owned corpus, no P@5 or nDCG number, and no absolute floor, against a reference that ships nDCG@10 ≥ 0.65 as a hard bar and a 0.8 extraction-recall floor with a non-zero exit. Against the stated bar of "the same level of accuracy," this is the row that makes every other row unauditable in either direction.

What is genuinely ahead of gbrain, and worth keeping: physical isolation as structure rather than policy — a separate Neon project is stronger than the sourceScopeOpts invariant, which is policy and has leaked twice; origin_context as an immutable credential-derived stamp, stronger than an agent-typed source line; MCP annotation hygiene, which gbrain sets nowhere; #3's "nothing renders unless a user action is attached to it," which correctly kills gbrain's decorative composite score; debt-triggered consolidation over a 300-second poll; and export-as-the-self-host format with a CI-gated round trip.

MCP, clients, and in-chat UI (2026)

MCP 2026-07-28 retires the initialize handshake and session IDs — servers deploy "behind a plain round-robin load balancer without shared storage." DCR is deprecated in favor of Client ID Metadata Documents.

MCP Apps is real and ratified. SEP-1865, proposed Nov 2025, shipped as the first official MCP extension on 2026-01-26 and folded into the extensions framework locked by the 2026-07-28 release; co-authored by Anthropic and OpenAI on top of the open-source mcp-ui project. The mechanism: a server declares a UI template as a resource under the ui:// scheme with mimeType text/html;profile=mcp-app plus a _meta.ui block; a tool links it via _meta.ui.resourceUri; the host advertises support at initialize through the io.modelcontextprotocol/ui extension capability and renders it in a sandboxed iframe; the view calls back over bidirectional JSON-RPC via postMessage, and every UI-triggered action re-enters MCP's normal tool-call consent path.

But it does not reliably render today. Claude shipped MCP Apps support on 2026-01-26 with launch partners, yet open bugs run through at least June 2026 (ext-apps#671, claude-ai-mcp#165/#471/#69): Claude negotiates the capability and fetches the resource but never mounts the iframe, falling back to a text placeholder. The OAuth constraint that settles the surface architecture

OAuth consent screens refuse iframe embedding by design. accounts.google.com sends X-Frame-Options: deny, and cross-site iframe cookie restrictions (Safari ITP, Chrome partitioning) break state handling further. Every real implementation — Claude Custom Connectors, ChatGPT connectors, generic MCP OAuth under RFC 8252 / OAuth 2.1 + PKCE — performs the exchange via a full top-level redirect or a separate popup, never an in-place iframe. Mobile is worse: PiP and widget surfaces get coerced to fullscreen or fail outright.

Consequence: "Connect Gmail" inside any AI client can only launch out to a real top-level page and redirect back. Connection management is inherently a normal web page with a real callback route.

Separately — and this is smaller than it first appeared. Gmail-class restricted scopes do require a Google-empanelled CASA Tier 2/3 assessment renewed every 12 months, but assessor pricing lands at $540–$1,800 per app with a 3–4 week turnaround. That is a scheduling item, not a strategic gate; Shortwave, a shipping Gmail-native AI client, simply runs its own verified app and takes the annual audit. The real cost is the calendar weeks, not the money.

The scope classes matter far more than the vendor. Calendar and Contacts have no restricted scopes at all — merely "sensitive," which is a brand review measured in days. drive.file with the Google Picker is non-sensitive and needs nothing. But every other Drive scope is restricted, including drive.metadata.readonly — there is no read-only middle ground — and all Gmail read scopes are restricted. Microsoft Graph has no CASA equivalent: publisher verification is free and takes 1–5 business days, making Outlook and OneDrive a materially cheaper first mailbox than Gmail.

Connector economics resolve on one vendor property. Pipedream Connect bills per unique external user rather than per connected account — three Google accounts for one user cost the same as one — at $99/mo for 100 users plus $2 each after: roughly $1.90/user at 1,000 and $1.99/user at 10,000. Composio is cheaper still on usage-based pricing but exposes you to call-volume creep. Nango lands near $3/user. Merge at $65 per linked account (~$195/user) and Paragon at five figures annually are both out. Pipedream is also the only vendor documenting a production shared-OAuth-app path — Nango and Arcade explicitly push you to bring your own client for multi-user production — though Pipedream was acquired by Workday in November 2025, which is its own kind of dependency risk.

Cloudflare as substrate

Credible for "separate DB, separate file store, per user, billed to zero when idle." D1: 50,000 databases/account, API-provisionable at signup, 30-day Time Travel PITR, $0.75/GB-mo — but 10 GB hard cap per DB, a 1 TB per-account default, and no native vector search. Neither D1 nor Durable-Object SQLite has any vector type, vector index or similarity function, and neither permits loadable extensions — FTS5, JSON and math only, confirmed against current docs and a full changelog scan, so sqlite-vec is unavailable and pgvector (a Postgres extension) is categorically impossible. Vectorize: 50,000 indexes/account, 20M vectors and 1,536 dimensions max per index, and no per-index charge — billing is stored and queried dimensions only, so index-per-user costs the same as namespace-per-user. ANN only; hybrid BM25 exists on Cloudflare but inside the separate AI Search product (formerly AutoRAG), itself built on Vectorize. Durable Objects: SQLite-backed, 10 GB each, alarms for per-user scheduling, JS heap warm between requests until eviction, no account storage cap. Workers: 128 MB memory on both Free and Paid — no tier raises it — CPU configurable to 5 min/request on Paid, WASM SIMD available. Workflows: GA, 50,000 concurrent instances, sleeping steps free. AI Gateway: per-user-ID spend caps. The Agents SDK speaks MCP 2026-07-28 statelessly with no session Durable Object. For the web app, the 2026 default is Workers with static assets (assets.not_found_handling = single-page-application) over Pages, with a thin /api/* prefix.

At 10,000 users on a plausible shape: ~$900–1,000/mo of Cloudflare, of which D1 storage is ~$750. LLM inference dominates at every tier — likely 10–100× the platform subtotal. R2 has no customer-managed per-object keys, and the Worker sees plaintext at unwrap time, so Cloudflare stays inside the trust boundary regardless of how encryption is arranged.

Cross-cutting principle: the brain is a data plane, not an agent

This governs how to read all nine cards, so it sits ahead of them. The agent is on the other side of the wire. It has the conversation, the user's immediate intent, and a frontier model. The brain has the corpus. Judgement belongs where the context is; bulk transformation belongs where the data is. Every argument for putting an agent inside the brain is an argument for spending your money on a decision the caller's model could make better.

The precise distinction is between an agentic loop and a model used as a function:

Agentic loopModel as a function
Control flowThe model decides what comes nextA fixed pipeline you wrote
Tool selectionYesNone
IterationUntil a goal is metOne call per item
CostUnbounded ahead of timeN items × 1 call — estimable
TestableBarelyAgainst a fixture corpus
ResumableHardTrivially, per item

Consolidation in #7 is entirely the right-hand column — "for each new item, extract entities with a fixed prompt and a structured output; for each entity, enrich; for each contradiction candidate, classify." That is a data pipeline that calls a model, not an agent. This is not pedantry: it is what makes #7's three guards possible at all. You can estimate cost before running only if fan-out is N×1. You can checkpoint only if items are independent. You can measure against a fixture corpus only if the pipeline is deterministic. The 53× cost incident is precisely what happens when fan-out stops being predictable.

The read-path rule, stated precisely

No unbounded, generative model call on the read path. A bounded scoring function over a fixed-size candidate set is fine.

An earlier wording — "no server-paid model call on the read path" — banned both, and that was too broad. It is why synthesize was correctly cut from #8, and it would also have banned cross-encoder reranking, which the parity audit identifies as the single biggest unclosed accuracy delta at 60% of top-1 results reshuffled. Those are different animals: synthesize takes corpus-scaled input, runs seconds to minutes, and a model's judgement decides when to fire. A reranker takes a fixed 100 candidates, runs sub-second, and fires deterministically on every query. Bounded, estimable, cacheable.

Consolidation may call models freely — it is batch, budgeted, checkpointed and measurable. The read path may call one, if it is a scoring function with fixed input size. Nothing anywhere runs a loop.

Two consequences worth stating. First, the thirteen cards the parity audit proposes are, almost without exception, not agentic AI features — they are retrieval engineering, data engineering, measurement, ops, cost control and trust. That is the category an ideation pass structurally misses, and it means the remaining work is known-shaped rather than invention. Second, the reranker is not free: at roughly $0.001–0.002 per query on a hosted API and ~1,500 queries per active user per month, it lands near $1.50–3.00/user/month against a $10–20 price point. That is 7–15% of revenue for the largest single quality lever available — probably worth it, and probably worth self-hosting a small cross-encoder on the consolidation fleet so it becomes compute rather than per-call API spend. Either way it is a line item, not a rounding error, and #8's "every remaining tool is SQL" claim no longer holds.

1.

One brain per person, physically isolated — and provable

axis: isolation confidence 88% complexity Medium

Give every user their own Neon project — one project, one branch, one database, one role — plus an R2 prefix for their markdown. The connection string is the isolation receipt: hand a skeptical user their own postgres://, let them run \l, and the promise is verified structurally in one command. No other candidate substrate can do that. Then publish a machine-readable register of every component that can touch more than one user's data and ship a signed prove_isolation readout naming the caller's own project id, database and storage prefix, with a public canary tenant anyone may try to read and watch fail.

The tenant unit must be a project, not a database. Neon's hierarchy makes this decisive rather than stylistic: databases-per-branch is capped at 500 on every plan including Enterprise, so database-per-tenant breaks at 500 users — and worse, every database inside a branch shares one primary compute endpoint. One tenant's re-embed contends with every other tenant's query, and scale-to-zero is impossible while any tenant in the project is active. Database-per-tenant is a tenant_id column with better ergonomics. Project-per-tenant gives each user their own compute, their own storage branch, their own PITR and their own connection string.

And it is cheap because idle is genuinely free. A suspended Neon project costs $0 compute and about $0.105/month in storage while remaining a separately-addressable Postgres. That is the fact that resolves the whole tension: isolation you can verify and near-zero idle stop being a trade. Set the suspend delay to 1 minute (a Scale-plan setting) and accept a ~500–870 ms wake on first connection per session.

Two operational pieces are load-bearing, not polish. Keep a warm pool of 50–200 pre-provisioned, migrated, empty projects — signup assigns one and stamps the user id rather than calling create-and-wait, because Neon publishes no SLA for create-project → create-role → create-database → first query. Pool idle cost is ~$21/month. And stagger consolidation by user-id hash across the night, bounded to ~20 concurrent tenants: consolidation is the only job that touches every project, and running it as a thundering herd converts idle users into active ones and trips Neon's API limits at the same time.

More decisively, Vectorize ships no BM25 at all, so two of the three recall arms would live in another store with no transaction spanning them — a page ingested but not yet indexed is visible to the full-text arm and invisible to the vector arm, and RRF silently fuses a partial universe.

external:Why not Turso, despite the best-fitted per-tenant story of any candidate: the engine with GA DiskANN vector indexing (libSQL) is the one being superseded, and its successor supports exact vector search only, with ANN on the roadmap and no date. Multi-DB Schemas — the migration fan-out for thousands of tenant databases — is deprecated for new users, and BM25 sits behind an experimental flag. Any one of those is survivable; all three on a substrate you cannot cheaply leave is not.

Rationale

Your bar is that people believe their data sits in separate databases and separate file stores only their agent can reach. Shared-database-plus-policy is a claim — "we enforce this correctly, everywhere, forever." A separate database is a fact a skeptic can test. The register and the attestation convert the fact into something checkable from outside, which is the only form of trust that survives the first incident anywhere in the category.

Downsides

This means not running the MCP server on Workers. A Hyperdrive config is pinned to one connection string and the account cap is 25 configs on Paid — the wall is at tenant #26, not #10,000. Neon's serverless driver routes around it, but the cleaner answer is that nothing about stateless MCP requires an edge runtime: a stateless Node or Bun fleet gets pooled TCP, prepared statements, a per-tenant connection LRU and full pgvector semantics, and each Neon compute's own PgBouncer accepts 10,000 client connections per endpoint. That is a real reversal of the Cloudflare-shaped assumption the rest of this document was built on, and it deserves an explicit decision rather than drift.

The ceiling is commercial, not technical. Scale's 1,000 projects covers 1,000 users; 10,000 costs 18 extra blocks at $900/month or an Agent-plan conversation; 100,000 is an enterprise negotiation with a company Databricks acquired for $1B — a stability signal and a pricing-power signal at once. Get the ceiling and the price above 30,000 projects in writing before selling a 100k-user roadmap, because if Neon won't commit on non-punitive terms the answer at that scale is self-hosted Postgres-per-tenant on CloudNativePG, which costs you the scale-to-zero that made idle cheap.

The most likely production bug is one line. pgvector defaults hnsw.ef_search to 40, and an HNSW scan returns at most that many rows no matter what LIMIT asks for. Port the schema without SET hnsw.ef_search = 250 per query and your 250-candidate pool silently becomes 40, RRF fuses a truncated universe, and autocut fires on a distribution that does not exist. gbrain documents this in src/core/vector-index.ts; inherit the lesson, not just the schema.

Two smaller cautions. A naive "consolidate everyone at 03:00" cron wakes every project at once and roughly doubles the bill. And Neon's AUP does not permit creating an account per signup to multiply free-plan resources — read the free tier as evidence that its envelope (0.5 GB, 100 CU-hr) is right-sized for a 4,000–6,000-page brain, then pay for it on one account.

prove_isolation appears nowhere in gbrain — verified by grep, so any claim that it comes "at zero extra cost" is false. It is new work. It also collides with the seven-frozen-tools commitment if shipped as a tool; ship it as an MCP resource. And do not run it live on every dashboard page load: that means deliberately generating cross-tenant authz failures at consumer traffic volume, on the hot path, with a permanent stream of denied-access entries in your own audit log. Batch it against the canary and serve a cached, timestamped result.

Extract, watch, re-implement — with a number for how far behind you are

axis: upstream replaces the container approach confidence 84% complexity Medium

brainz owns 100% of its code. gbrain is a reference to learn from. The mechanism is three parts, and the order matters because each one is cheap enough to survive the month it ships in.

First, be gradeable over the wire. gbrain already ships a conformance runner that speaks to any MCP endpoint: gbrain protocol conformance --target https://… --token <tok> connects over StreamableHTTPClientTransport, calls listTools, exercises each verb, and emits a JSON report against the response and error schemas. Point it at brainz's hosted /mcp in week one and you get contract conformance for zero adapter code — a CI job, not a project. When it goes red, you are behind on something upstream considered load-bearing enough to certify.

Second, read the changelog, not the code. CHANGELOG.md is 23,231 lines against operations.ts's 6,449 — and it is hundreds of releases of already-distilled rationale written by the person who made the decision, in a stable shape (plain-English headline, before/now table, "Things to watch:", "To take advantage of vX", and itemized path-scoped bullets). The code tells you what; this is the only place the why survives. Run it newest-to-oldest once, collapsing supersessions, to produce a dated concept snapshot pinned to a commit SHA — that is your bootstrap. The SHA then turns the ongoing watcher into a pure delta job with a resumable cursor. Each week, intersect the release's touched paths against a watch set before spending any semantic reading; only survivors get read.

Third, every "not yet" is an artifact with an expiry date. One upstream/concepts.jsonl holds a row per gbrain concept — implemented(where) / omitted(reason_code, revisit_by) / not-yet(priority) — and CI fails when a watcher-detected concept appears in none of the three, and when a revisit_by date passes. That second check is the whole mechanism: brainz's omissions are overwhelmingly "not on this substrate yet," and every constraint that would drive one is a moving number. Make reason_code a closed vocabulary (substrate:no-bm25, substrate:worker-mem-ceiling, product:consumer-not-operator, policy:frozen-tool-surface) and after thirty omissions the ledger is a queryable design-constraint corpus — "eleven omissions trace to one ceiling" becomes a substrate-migration argument produced as a byproduct of saying no.

gbrain's scar tissue lands in the same table. Each of the 42 scripts/check-*.sh guards becomes a row — {failure_mechanism, what_masked_it, brainz_analog, guard, status} — and every unported one ships as a skipped test with a reason string, so the suite prints the unguarded-hazard count on every run. The translations are concrete: dev-engine-masks-remote-engine becomes a parity test that must run against remote; unhandled rejection in a detached timer becomes uncaught async in an alarm handler; check-progress-to-stdout.sh becomes "anything non-JSON-RPC on the MCP stdio stream," the most common way a local MCP server dies silently.

Too wide … trains the operator to ignore the warning," plus "Adding to this list REQUIRES a CHANGELOG line so coverage grows deliberately." gbrain has already solved the watcher signal-to-noise problem once, in the open, with governance attached.

Expect to assemble this rather than adopt it.

Rationale

Rejecting the container was right, but it changes the failure mode rather than removing one. A runtime dependency fails loudly; a soft dependency decays quietly. ffmpeg/libav and OpenSSL/BoringSSL did not diverge because anyone decided to stop tracking — they diverged because nobody could see how far behind they had drifted. Every mechanism here is chosen for the same property: it fails a build rather than producing a digest someone is supposed to read.

Downsides

The path gate is narrower than it looks. I checked drift-watch.ts: RETRIEVAL_WATCH_PATTERNS has six entries, all retrieval-quality. Nothing about auth, security or schema — oauth-provider.ts, migrate.ts and the engine files, which CLAUDE.md itself flags as the highest-stakes surfaces, are unwatched. So the appealing "watch their filter and inherit their governance" property applies only to the retrieval slice; the rest of your watch set is yours to maintain, with no self-updating property.

The bootstrap is itself a cost-explosion risk. "Collapse supersessions across 23,231 lines" is an unbounded cross-referencing task — exactly the shape that produced the $50.71-vs-$0.96 incident. Chunk per release, estimate before running, and refuse over budget.

The hazard corpus is thinner than it sounds. Across all 42 guards, only 2 contain masking language and 1 carries a quantified production cost. The two best examples are the two I quoted. Most cards will ship with empty what_masked_it and cost fields — real value, a one-afternoon bootstrap, but not 42 gems.

BrainBench is a much bigger commitment than wire conformance, and they should not be conflated. Its existing adapters (claude-code, codex, openclaw) are all thin wrappers over the same gbrain engine, differing only in injection shape. A brainz adapter needs an independent extraction, write-back and entity-resolution engine on D1+Vectorize before fixtures produce non-trivial scores — months, not a week-one shim. And tracking adapters/shared.ts reintroduces code-level coupling to a repo you have declared reference-only. Pin the fixture hash and accept lag, or you have a soft fork.

The ledger is the most process-shaped thing in this document and therefore the most abandonable. If the CI date check is ever made non-blocking "just for this sprint," the whole mechanism is decorative within a month.

3.

Manage in the chat panel; step out only for consent

axis: surfaces new confidence 80% complexity Medium

4.

Context is a credential stamp, not a user tag

axis: context confidence 87% complexity Medium

Personal and work live in the same store, marked — but the mark has to be derived, not asserted. Stamp every row with an immutable origin_context computed from the connected account that produced it (provider + account_id + issuer), never a user-typed tag and never editable by an agent.

Then split it in two, because origin and subject are different questions. A dentist appointment on your work calendar has origin=work, subject=personal; a job offer in personal Gmail is the reverse. Access fencing runs on origin only — cheap, provable, fail-closed. Ranking, categorization and briefing composition use subject — inferred, multi-valued, confidence-scored, mutable. The hard rule: a subject inference may narrow what a caller sees; it may never widen it. Never put an LLM guess on the access-control path.

Three consequences follow. Derived rows inherit the union of their inputs' contexts — otherwise the nightly cycle reads both halves, writes an unlabeled synthesis, embeds it, and you have built a laundering machine. One entity, many context-faceted claims — a colleague who is also a friend is one alice-example with two facets, because two entities makes "when did I last talk to Alice" unanswerable and no primitive exists to stitch them later. Severance is a state transition, not a delete — leaving a job purges artifacts ingested through the employer's credential, preserves entity identity and user-authored facts, and re-derives every mixed artifact with the tombstoned contributions removed.

This is also how enterprise works. In ChatGPT Work the admin approves one connector per workspace and tool definitions freeze at approval, so connector identity cannot be per-user. Separate the two acts: the admin approves the connector, each employee claims a brain. The grant issued through the work connector is minted to read origin: work only, so the personal half is structurally invisible from the employer-approved path rather than filtered in UI. 7.

Dream while the compute is already awake

axis: runtime confidence 82% complexity Medium

A nightly cron means 10,000 model cycles per night whether or not anything changed. Invert it: the brain accrues consolidation debt — unconsolidated facts, unresolved contradictions, merge candidates — and a cycle fires when debt crosses a threshold or ages past a ceiling. A user who added nothing pays nothing.

Per-tenant databases break the obvious trigger, and that is load-bearing. With one shared database you would ask "who has unconsolidated facts?" in a single query. Across 10,000 separate Neon projects there is no cross-tenant query, and waking every project to ask is the thundering herd. So a control plane is forced: one shared Postgres holding no user content, one row per user — last_consolidated_at, pending_debt, next_due_at, tier, a reference to their connection string. Writes increment that row as a side effect; the scheduler asks that table who is due. It is one cheap query, and it is the only place a cross-user question can be asked.

Then the scheduling insight the substrate hands you: consolidate while they are active, not at 3am. A cycle costs a compute wake (~500–870 ms) plus the compute-seconds it runs. If the user is mid-session their project is already awake and you pay neither. And a user who just finished a long conversation with their agent is precisely the user with fresh debt. So the default trigger is opportunistic — debt above threshold and compute already warm — with a time ceiling as the backstop for dormant brains, those staggered by user-id hash at ~20 concurrent. This inverts the sleep metaphor deliberately: you consolidate in the conversation's aftermath, not overnight.

It runs on its own fleet. Cycles last minutes, need real memory for embedding batches, and must not autoscale on request volume — so a stateless worker fleet pulls from a queue, opens one user's connection string, runs the cycle, closes. Separate from the MCP request fleet for the same reason MCP moved off Workers.

The cycle runs cheap-to-expensive so a budget ceiling truncates into a coherent state rather than a failure. Deterministic phases first — dedup, link resolution, staleness marking, rule-based entity merge, embedding-space clustering — none of which calls a model. The free tier stops there, which makes the free/paid boundary a mechanism rather than a quota, and writes its own upgrade prompt: "your brain found 14 contradictions it can't resolve without thinking." Then the model phases: extraction, enrichment, contradiction resolution, salience scoring. Then materialize exactly what a model produced — salience, entity cards, the contradiction set, extracted commitments — because that is what the live briefing in #5 reads. Truncating after the deterministic half leaves a brain consolidated but not dreamt, which is a state you can describe to a user.

Downsides

Rationale

Three corrections do the real work. The endpoint fix turns per-client tailoring from a self-reported-header gamble into an install-time choice bound to an OAuth grant. Cutting synthesize forfeits the demo. manage's invisibility is unresolved. Whether hosts forward tools/call for a name absent from tools/list is unconfirmed. If they refuse, it becomes the eighth advertised tool at ~700 tokens on every request — safe, since a model has no nonce and gets invalid_params, but the "no model sees more than seven" claim becomes eight, one of which is noise for the model.

recall(entity:) and the entity tool overlap, and this revision did not remove it. That is a live instance of the overlapping-tools failure the card cites elsewhere.

Two endpoints means two golden manifests and two conformance profiles, and the cross-surface equivalence test covers ranking and body equality but not authorization. Whether OpenAI's connector review accepts a /openai surface carrying five tools beyond the mandated two is unconfirmed — no review-policy document surfaced. If a reviewer requires the compatibility pair alone, then entity, briefing, remember, forget and brain must ride inside fetch's id grammar on that endpoint: workable, materially worse, and a redesign of half this card. The enterprise freeze's granularity is likewise unconfirmed, so the design assumes conservatively that a description edit costs a re-scan.

The 8-param budget is a judgment call, not a measurement, calibrated on one codebase's most-loaded verb — and gbrain's +13–17pp hierarchical-dispatch result was measured on markdown routing tables, not live tools/list selection. If the number is wrong it is probably too generous.

Downsides

The connector layer is still not solved, and this idea assumes it exists eventually. Gmail-class scopes need CASA Tier 2/3, re-certified annually, on a multi-week timeline. Connector vendors are priced for B2B tenant counts. Two escape hatches were generated and both are weaker than they look: borrowing the client's existing connectors assumes cross-server OAuth token sharing that no evidence supports, and a per-user ingest email trades OAuth cost for spam, spoofing and deliverability infrastructure nobody has priced.

The whole shape presupposes brainz builds OAuth connectors at all. If the answer is "file and folder sync forever," the CASA argument is moot and this collapses to ordinary onboarding advice. Decide that before scoping it.

The authority file is a product surface with real maintenance cost and its own accuracy liability, and it must flow strictly one way or it silently becomes a cross-user channel.

Contradictions to resolve before building

1 and 2 — resolved by the #8 revision. Both prove_isolation and brain-wide inventory counts now live in the read-only brain tool, with the attestation additionally stamped into _meta on every response. The earlier resolution — "ship them as MCP resources" — turned out to be unavailable: the grounding pass found model-initiated resource access exists on only one of the four target clients, so a resource would have been unreachable for most users. Recording it here because the reasoning generalizes: any capability parked on resources needs the same check.

3. Zero-knowledge encryption vs. server-side synthesis (#5, #7). LLM calls need plaintext in the compute plane — including BYOK. A service that genuinely "cannot read your files at rest" cannot also run consolidation. The honest maximum: no decryptable key at rest on our side, plaintext only inside one isolate for one authorized request, and a receipt each time. Pick that and say it precisely, or drop the claim.

4. Cold storage (#7) vs. the entity() p99 < 100 ms promise (#8). A hydrate-on-demand brain cannot honor a sub-100ms guarantee on first touch. Scope the SLA to warm brains, or scope eviction to brains with no live client connected.

5. Hard-delete on revoke (#6) vs. forget's never-delete semantics. Two deletion semantics in one product; users will hit both. #6 makes the hard delete cheap because derived data is rebuildable — but it must be an explicit decision, not an emergent one.

6. Gateway-enforced spend caps vs. BYOK privacy. Per-user-ID caps from a vendor gateway require routing the user's own provider key and raw prompt text through a third-party proxy. gbrain's own gateway instantiates native providers with no baseURL — direct to provider. "Your memories transit our AI vendor's proxy so we can meter you" is a privacy regression traded for a billing convenience. Name the trade before adopting it.

7. Origin-fenced work grant (#4) vs. one-D1-per-user (#1). #1's isolation unit is the person; #4's fence is the origin. Together they place employer content inside a consumer-owned database — technically sound, legally unexamined. Not an engineering contradiction; an unowned product decision.

P1.

The brain ships the instructions that make the agent use it

criticalcomplexity Lownew card

Nothing in the nine ideas causes the brain to be read or written. remember is "the single create path" called by a caller nobody instructs; recall is a ranked read the host model has no directive to reach for. gbrain's two most load-bearing behaviors are not tools at all — a signal-detector that fires on every inbound message (capture) and a brain-first rule before answering anything about a person (retrieval). Both live in a skills layer this design deleted as operator machinery, without replacing the mechanism.

The failure compounds rather than degrades: no writes → no consolidation debt → no cycles → no salience, entity cards or contradictions → #5's live briefing assembles over an empty materialized layer, and #7's "14 contradictions" upgrade prompt has nothing to count. A brain that is technically correct and never invoked is indistinguishable from no brain, while still billing you for consolidation.

The mechanism costs zero tool names: MCP's server instructions field, plus the tool descriptions, plus #8's response envelope. A capture-and-consult directive the brain ships to whichever client connects. Treat it as a versioned asset under #8's manifest-epoch rule — descriptions freeze at enterprise approval, so this is a dated release, not prose someone edits on a Tuesday. And it needs the same evaluation as any other quality lever: a held-out intent fixture set with strict and lenient scoring, CI-gated, since gbrain's own +13–17pp routing result was measured on markdown routing tables rather than live tools/list selection.

P2.

Ranking is a stack, not a query

criticalcomplexity Highnew card

gbrain's answer quality does not come from pgvector + tsvector + RRF. It comes from roughly nineteen stages that run after the candidate pool exists. This design commits to two of them unambiguously, half-commits to four, and does not mention thirteen. Every one of the missing stages fails silently — answers get quietly worse and nothing errors.

The unmade decision underneath most of them is one question: does recall get a rerank call and a query embedding, and who pays? The cross-cutting principle above answers the "may we" — a bounded scoring function over a fixed candidate set is permitted. What remains is the number: roughly $1.50–3.00 per active user per month on a hosted reranker, or compute if you self-host a small cross-encoder on the consolidation fleet.

What has to be built

A shared normalizer (NFKC + lowercase + whitespace) applied on write and read — the only thing keeping alias and title matching from drifting between index and query. Intent classification as a ranking input, not just the relational router #8 committed to: it sets the fusion weights, the effective RRF k, the exact-match boost and the recency tilt. Without it "who is Bob" and "what did I say last week" rank identically, which is most of what a consumer asks. Query-vs-document embedding asymmetry — both leading providers are asymmetric, and using the document encoder for queries quietly degrades every search.

The alias hop — exact-title, then alias table, then slug-suffix — is the only layer that bridges true synonyms with zero surface overlap. Nicknames, maiden names, "the Acme deal": the consumer case is heavier than gbrain's. Cross-encoder reranking reshuffles 60% of top-1 results on a real corpus and fails open, which makes it the single biggest unclosed delta with a purely economic objection. Autocut must read the rerank score, not the RRF gap — gbrain measured the alternative at 0.602 versus 0.569 and concluded it is mechanical decay rather than signal, so porting autocut onto RRF gap cuts on noise and is a precision regression with no error.

Title-phrase boost is the most visible failure when absent, and doubly so here: OpenAI's mandated search projection returns {id, title, url}, so on that surface the title is all the user sees. Per-prefix recency decay (14–60 day half-life on churn content) matters because consumer queries are overwhelmingly temporal and the committed connectors — mail, calendar, chat — are exactly the high-churn content. Source-type boost and hard excludes are gbrain's first line of defense against contradictions, settled by ranking before any model phase adjudicates; note this requires letting origin inform rank, which #4 currently forbids, so that card needs amending.

Graph adjacency and cross-source corroboration is where brainz is uniquely advantaged — origin stamps make "calendar and mail both attest this" free, and gbrain has no equivalent signal. The compiled-truth boost (2.0× on a canonical summary chunk) is why "who is Sarah" returns the current-state answer instead of 200 raw emails — and #7's consolidation output list contains no canonical summary chunk today, so this is a change there too. Four-layer read-time dedup — top-3 per page, 0.85 Jaccard, a 60% page-type cap, 2 chunks per page — stops one verbose page monopolizing the answer; mail threads and chat transcripts are near-duplicate-heavy by nature, worse than a curated wiki. Plus return policy (intent-adaptive sizing), evidence and create_safety on the envelope so the writing agent knows whether the thing already exists, and contextual-retrieval wrapping at embed time, which matters most on exactly the short fragments a mailbox produces.

P3.

Measure the answer, not the wire

criticalcomplexity Mediumnew card

#2 grades the wire — tool lists, response schemas, error envelopes — and it will pass green while write-back drops a fact, while recall misses something injected two sessions ago, or while a bad extraction prompt degrades every briefing every user reads. Keep the two explicitly separate so they are never conflated: conformance proves you speak the protocol, and proves nothing about whether the answers are right.

Against the stated bar of "the same level of accuracy," this is the row that makes every other row unauditable in either direction. What is needed: an owned fixture corpus; a regression arm and an absolute floor (gbrain ships nDCG@10 ≥ 0.65 as a hard bar); named-entity gates in the shape gbrain uses — title-substring Hit@1 ≥ 0.95, alias Hit@1 ≥ 0.98, dilution Hit@3 = 1.0; an extraction recall floor (0.8, non-zero exit); and grading of what consolidation produced, which is stored rather than recomputed — so a bad prompt is permanent and invisible.

Two structural choices decide whether this survives its first quarter. Split the suite into a deterministic always-blocking half (seeded PRNG, zero model calls) and a sampled model-judged half on the canary — otherwise a noisy, model-priced gate gets marked non-blocking within a month, which is the exact death #2 predicts for its own ledger. And set per-question-type floors rather than an aggregate: brainz's query mix is unusually heterogeneous — relational, named-entity, temporal, context-fenced — and an aggregate is especially good at hiding one collapsed category that users experience as "it never remembers people."

Per-tenant, across 10,000 isolated databases, the only quality signal that works is content-free telemetry: production avg_rank1_score drift. And give #1's canary tenant a second job — a nightly fixture run through the real /mcp on the real substrate, which doubles as the continuous post-deploy path check for extensions, GUCs (note ef_search is per-connection and can evaporate), indexes, the queue, and opening a tenant connection string.

P4.

The write path: what happens before the tool returns

criticalcomplexity Mediumnew card

#8 says "SQL plus a sub-cent embedding on write." #7 says extraction is "a queue entry, not an inline step after a write." Nothing says where chunking, link extraction and fact embedding actually sit — and until that split is named, those two cost claims cannot be reconciled and every chunking capability is homeless.

gbrain's split is deliberate and worth copying: facts embed synchronously, so downstream classifiers have vectors immediately; chunks are backfillable; and links are watermarked. One correction to gbrain's shape rather than a copy: link extraction being async means "who did I just say Alice works with" answers wrong immediately after being told. Make it synchronous or sub-second, and make it reconcile rather than accumulate — removing stale edges, not just adding new ones.

Three specifics that are cheap now and unfixable later. There is no chunking spec at all — pick one chunker deliberately and record the choice, since it is quality-affecting even when only one ships. A hard 6,000-character safety cap: gbrain hit two production bugs where over-limit chunks failed embedding forever, silently. And CJK-aware sizing — at ≥30% CJK, switch to per-character counting; without it CJK text counts as one giant word, overflows the embedder, and the page imports but never becomes searchable. A consumer product going global inherits that on day one.

Finally, contextual-retrieval wrapping — prefixing each chunk with its document title and a synopsis at embed time. The title tier is free and belongs on the write path; the synopsis tier is a model call and belongs in #7's model phase.

P5.

Decide the schema before the first project is provisioned

criticalcomplexity Lownew card

Four decisions are per-tenant, made at provision time, and unfixable by an optional argument. #8's additive-forever escape hatch future-proofs the tool surface; it does nothing for the storage layout. Every one of these gets baked into every project you create, starting with the first.

FTS language. It configures the write-side trigger functions, so changing it means recreating triggers and backfilling the whole tenant. Ship an English default silently and every non-English user runs one of three recall arms through an English stemmer, permanently, with no signal that anything is wrong. The image embedding column. Adding a second vector column later is a schema migration across N databases (see P6), not a parameter — decide now even if the feature ships later (P12). Embedding dimensions. pgvector's HNSW index caps at 2,000 dimensions for vector (4,000 for halfvec), which makes several plausible defaults unindexable. Taxonomy version, since brainz owns taxonomy centrally once schema packs are dropped.

On the model itself: name it and record the measured basis. gbrain's answer is directly transferable and both halves of it are load-bearing on cards brainz has already committed — ZeroEntropy zembed-1 at 1280d, which beat OpenAI on 11 of 20 and Voyage on 4 of 20, at 442ms versus 973ms and $0.05 versus $0.13 per million. Latency matters for entity's promise; price matters for P7. Also stamp a per-page provenance signature so that a same-width model swap re-embeds only the affected pages rather than the whole fleet.

P6.

Migrate ten thousand databases without waking them

criticalcomplexity Highnew card

gbrain runs 120 ordered migrations against one database. brainz must run them across N databases, most suspended at $0 and requiring a paid wake to touch, with partial-failure states the stateless fleet has to tolerate at request time. The substrate comparison rejected Neon's Multi-DB Schemas partly over migration fan-out — the fan-out did not disappear, it moved here.

Build it on #7's existing machinery rather than a second system: a schema version on the control-plane row and the same warm-compute-opportunistic trigger. A tenant whose compute is already awake migrates for free; dormant tenants migrate on their next wake, or on a bounded sweep at the same ~20 concurrency. The request path must tolerate finding a tenant behind — either migrate inline before serving or fail with a typed error the fleet retries, but never serve against a schema it does not understand.

The half that is not migration at all: per-tenant feature flags. Without them a new chunker or a revised extractor prompt can only ship all-at-once across every isolated project — no canary, no staged rollout, no way to compare. That is the mechanism P13 needs, and it belongs on the same control-plane row.

P7.

The first import is the biggest bill you will ever send

criticalcomplexity Mediumnew card

#7's budget cap is debt-triggered and therefore never sees the one event that dwarfs everything after it. First Gmail connect is tens of thousands of items to chunk and embed in a single burst, for a flat-priced user, on a 0.25 CU compute. At $10–20/month, COGS per user is the business model, and this is the moment it is decided.

gbrain's pre-flight gate is delta-aware, prompts interactively, and auto-defers to a capped background job when non-interactive. The consumer form of that prompt is not a guard, it is a product moment: "importing 41,000 emails — start with the last 90 days?" That is a better first run than a progress bar, and it halves the bill. Pair it with a bounded first window by default and a visible way to widen it later.

Two mechanisms go with it. A rolling per-tenant spend counter on the control-plane row — which already carries tier and pending_debt and which the scheduler already reads, so this is a column rather than a system. And a hard fail on an unpriced model: gbrain's budget tracker refuses to proceed when a cap is set and the model is absent from the pricing map, because an unmetered path does not surface as an error, it surfaces as a bill.

P8.

Nothing the model wrote is true until something says so

criticalcomplexity Mediumnew card

gbrain assumes an operator who promotes or rejects auto-extractions and demotes everything unverified until they act. brainz has no operator by construction — #3's action enum has no review verb and #9 deletes the CLI. So essentially 100% of derived knowledge is "unverified" in gbrain's sense, ranked as if the user had typed it, with no flag for the consuming model to weigh it by.

Three mechanisms close it. A trust level carried on the origin stamp — #4 makes origin a fence only; it should also say whether a claim was stated by the user, extracted by a model, or inferred. A confidence gate on automated mutation, in gbrain's explicit shape: ≥0.8 auto-apply, 0.5–0.8 queue for review, <0.5 skip and log. And a one-tap confirm/reject through the envelope and the panel, since a review queue with no reviewer is just a slower gap.

One naming change in #7 is a real decision, not a wording fix. That card calls its phase contradiction resolution. Silently overwriting a user's recorded opinion with a model's judgment is the most trust-destroying write a memory product can make, and gbrain's equivalent phase is deliberately report-only. Make it report-only here too and let the user resolve.

Two guards, both absent. Prompt-injection sanitization in and out — Gmail bodies are attacker-authored text flowing into durable memory the user's agent later reads back, which is a direct injection channel into their assistant. And an anti-loop guard: #7's cycle reads the store it writes, so the self-extraction loop is structurally present and unguarded — a model phase extracting facts from its own prior output drifts with nothing reporting it.

P9.

Undo, versions, and the delete that actually deletes

criticalcomplexity Mediumnew card

The design has no data lifecycle. No page versioning or revert. No soft delete, restore, TTL trash or hard purge. No blast-radius preview before a destructive operation. And no erasure path — forget is expire-not-delete and explicitly distinct from account deletion, which is left undefined across Neon, R2 and the control plane.

For a consumer product this is simultaneously the legal surface and the most trust-critical behavior in the product, and the sentence that names it is: undo, after a nightly model phase rewrote something you told it. P8 reduces how often that happens; this is what you need when it happens anyway.

gbrain's shape ports directly: three layers on every destructive op — impact preview, typed confirmation, soft-delete with a TTL — plus a 72-hour tombstone cascading to chunks, links and relations, and get_versions / revert_version on a page. Note this makes #4's severance a destructive operation with neither preview nor undo today, and severance re-derives every mixed artifact — so the preview must show what will be recomputed, not just what will be removed.

P10.

Ingestion is a substrate, not a connector list

criticalcomplexity Highnew card

"Automatic ingest and background synthesis" is currently manual-by-proxy — #3's own downside concedes there is no ingestion substrate. Missing: recurring pull, per-source cadence, idempotent staggered retries, per-source locking, resumability. Missing more consequentially, a per-item ingest log — not a nicety, since #3's "nothing new from this source in 23 days" and #9's "a specific statement of what is not indexed yet" both structurally require it.

Preserve the raw payload. #6's exported file is the rendered page, not the connector's original. Without the original, re-deriving every page with a better extractor after a prompt improvement is impossible fleet-wide — which means every extraction-quality improvement applies only to content ingested after it shipped.

Conversation content has no path in at all. An MCP server sees tool calls, not transcripts, so the thing gbrain's synthesis phase exists for cannot reach brainz through the protocol. The one path that works is the one brainz has not designed: bulk import of a user-uploaded chat export. Both Claude and ChatGPT offer data exports; parsing one is a well-defined job and the only way conversational memory arrives in volume.

Widen the worker fleet from one queue with one job class into a typed job runner — consolidate, ingest, export, backfill, re-embed — with re-enqueue on worker death, stall detection, max-attempts dead-lettering, and poison-job protection, since under debt triggering a tenant that crashes the worker is permanently due. Note the lock-renewal hazard specifically: gbrain lost ~39 worker processes per day to renewals over a pooled connection, and a per-tenant connection LRU reproduces exactly that shape.

P11.

Junk is most of what a mailbox contains

importantcomplexity Lownew card

A Gmail corpus is majority newsletter, receipt and notification boilerplate. With no ingest-time sanity gate, all of it gets chunked, embedded, paid for, ranked, and consolidated over. This sits upstream of every ranking and dedup finding in P2 — the cheapest quality improvement available is not indexing the junk in the first place, and it is simultaneously the cheapest cost reduction.

gbrain's shape is a content-sanity pass plus a two-marker quarantine: hidden entirely, versus warned-but-still-searchable. The distinction matters because a receipt is junk until the day you need the receipt.

One guardrail seam to answer deliberately rather than by default: classification is either cheap heuristics you run yourself, or a model call — and if it is a model call, "do we send your mail body to a third-party classifier" is a question the isolation story in #1 has to answer out loud rather than in a subprocessor list.

P12.

Screenshots are memory too

importantcomplexity Mediumnew card

The dominant consumer image is a screenshot, and a screenshot is mostly text. "Find the screenshot with the wifi password" is a real query that fails completely today. There is also no stated policy for what remember does with a PDF, a voice memo or a photo — which happens in week one, not year two.

OCR-to-text is the minimum viable answer, and it is a model call, so it belongs in #7's model phase rather than the write path — consistent with the cross-cutting principle. Text extracted from an image then flows through the ordinary chunk-and-embed path and is retrievable by the same stack as everything else, with no image-vector arm required.

Record the image-embedding arm as a dated omission with a revisit_by in #2's ledger — but make the schema decision now (P5), since adding a second vector column later is a migration across every tenant rather than an optional argument.

P13.

A brain that changes overnight should say so

importantcomplexity Lownew card

A gbrain user runs the upgrade: they get a banner, a migration skill, and a self-upgrade audit trail. A brainz user's memory changes behavior overnight with no notice, no changelog channel, and no consent — and under P8 a model phase may have rewritten something they wrote. Managing the infrastructure is the deal being offered; changing what someone remembers without telling them is not part of it.

What that needs: a change record per tenant — what shipped, what it did to your memory, and what you can do about it — surfaced through brain so it is model-reachable rather than panel-only, and staged through P6's per-tenant feature flags so a change reaches a canary cohort before the fleet.

The same channel carries the growth surface. In a product with no docs, no CLI and no settings screen, capability discovery is the only way a user learns what their brain can do — which makes this the one card here that is also a product feature rather than only a safeguard.
