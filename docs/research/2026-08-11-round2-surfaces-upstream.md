## RESEARCH: MCP UI surfaces

**Research value: high** -- the MCP UI mechanism and the OAuth-in-iframe constraint are both concretely documented and directly determine this product's architecture.

### MCP UI extensions — the actual mechanism
Ratified as an official extension (not core spec) via **SEP-1865 "MCP Apps"** — proposed Nov 2025, shipped as the first official MCP extension Jan 26 2026, folded into the extensions framework locked by the **2026-07-28** spec release. Co-authored by Anthropic + OpenAI, built on the earlier open-source `mcp-ui` project.

Mechanism: a server declares a UI template as a resource under the **`ui://`** scheme (e.g. `ui://weather-server/dashboard`) with **mimeType `text/html;profile=mcp-app`**, plus a `_meta.ui` block (`csp`, `permissions`, `domain`, `prefersBorder`). A tool links to it via `_meta.ui.resourceUri` + `_meta.ui.visibility`. The host advertises support during `initialize` via extension capability **`io.modelcontextprotocol/ui`**. The host renders the template in a **sandboxed iframe** (`allow-scripts allow-same-origin`), with CSP built from declared `connectDomains`/`resourceDomains`/`frameDomains`. The view calls back into the server over **bidirectional JSON-RPC 2.0 via `postMessage`**: view→host methods `tools/call`, `resources/read`, `ui/open-link`, `ui/message`, `ui/request-display-mode`; host→view notifications `ui/notifications/tool-input|tool-result|tool-cancelled|host-context-changed`. Every UI-triggered action re-enters MCP's normal tool-call/consent path.

Note OpenAI's ChatGPT-specific channel uses a **different mimetype, `text/html+skybridge`** (its own "Skybridge" bridge-script runtime, `openai/outputTemplate` metadata) — parallel to, not identical with, the ratified `text/html;profile=mcp-app`. Whether/when OpenAI converges on the cross-vendor mimetype is `[unconfirmed]`.

### OpenAI Apps SDK
Built on MCP as a ChatGPT-specific superset: server exposes MCP tools + `ui://` skybridge resources; the widget gets **`window.openai`** — reads `toolInput`/`toolOutput`/`displayMode`/`theme`/`widgetState`, writes via `setWidgetState`, calls other tools via `callTool`, plus `requestDisplayMode`, `openExternal`, `sendFollowUpMessage`, `selectFiles`. Three **display modes**: `inline` (in message flow, adjustable height), `fullscreen`, `pip` (persistent floating window, **Web Desktop only — auto-coerced to fullscreen on mobile**, no true phone PiP).

Submission: verified developer account → OpenAI Developer Platform submission (MCP details, "developer mode" screenshots, directory metadata, country availability) → human review with **no published SLA**. **ChatGPT Work** (launched July 9 2026) and Enterprise/Edu: connectors and custom apps are **off by default**, admin-enabled, with role-based build/publish/run controls and per-connector action scoping (all/read-only/custom). An Aug 2026 change retires individual-user sync in Enterprise/EDU in favor of admin-managed sync.

### Claude client capabilities
Claude shipped MCP Apps support Jan 26 2026 (web + desktop), day-one with partners including Asana, Box, Canva, Figma, Slack, monday.com; VS Code Insiders/Goose/ChatGPT followed the same week. **However**, open bug reports run through at least June 2026 (`anthropics/claude-ai-mcp` #165, #471, #69; `modelcontextprotocol/ext-apps` #671): Claude negotiates `io.modelcontextprotocol/ui` and fetches the resource but **never mounts the iframe**, falling back to a text-only "[interactive widget rendered]" placeholder. No confirmed fix was found as of this research — treat third-party MCP Apps rendering in Claude as **currently unreliable in practice**, `[unconfirmed current status]`.

**Claude Artifacts** is a separate, older surface: a captured single-page HTML/React/SVG/Mermaid output with no arbitrary backend by default; 2026 added connector-backed artifacts that fetch on load / refresh on interval — Anthropic's own runtime-capability mechanism, distinct from MCP Apps' `ui://`. **Custom Connectors** (remote MCP over Streamable HTTP + OAuth) give tool-calling access to a private server; they do not imply a rendered UI unless that server also implements MCP Apps. No documented PiP-equivalent for Claude.

### Where OAuth connection flows have to live
OAuth login pages refuse iframe embedding by design — `accounts.google.com` sends `X-Frame-Options: deny`; cross-site iframe cookie restrictions (Safari ITP, Chrome partitioning) break session/state handling further. Every real implementation — Claude Custom Connectors, ChatGPT connectors, generic MCP OAuth (RFC 8252, OAuth 2.1 + PKCE) — does the exchange via a **full top-level browser redirect or separate popup**, never an in-place iframe form. Claude registers one fixed callback (`https://claude.ai/api/mcp/auth_callback`) across web/desktop/mobile/Cowork; ChatGPT's "in-chat OAuth" pops a temporary out-of-frame link mid-conversation and returns control after — the credential never transits the model.

**Consequence:** the "connect Gmail/Calendar/Notion" action inside any AI client can only launch OUT to a real top-level page, then redirect back. Connection-management UI is therefore inherently a normal web page with a real callback route — reinforcing a thin web dashboard, not an in-chat widget, as the place auth state gets authored. Mobile makes embedded contexts worse (PiP/widget surfaces get coerced to fullscreen or fail); native OAuth (system-browser view, RFC 8252) is the safe pattern there too.

### Thin management-shell patterns
The product-lives-elsewhere shape (CLI/MCP server/agent as the real product) still needs: login, a connections list with live status, a usage/budget meter, billing, and the OAuth callback route — that's the entire web surface. **Minimum viable Cloudflare stack (2026 default):** Workers + static assets serving a compiled SPA, `assets.not_found_handling = single-page-application` so client routes are free/edge-cached, with a thin `/api/*` prefix (via `run_worker_first`) handling only OAuth start/callback, session issuance, status reads proxied to the real backend, and billing webhooks. Cloudflare now steers new projects to **Workers-with-assets over Pages** for this exact shape. Keep the dashboard's own login (cookie/session or Clerk/Auth0-style) conceptually separate from the third-party OAuth tokens being managed — two different OAuth relationships terminating in one UI.

### Hard constraints and disqualifiers
- Never attempt to render a provider's OAuth consent screen inside any iframe (MCP widget or your own) — blocked by the provider's frame-ancestors/X-Frame-Options policy.
- Don't make MCP-rendered UI the primary account-management surface today: the mechanism is specified, but Claude's actual third-party widget rendering has unresolved bugs as late as June 2026. Build the web dashboard as the control plane; treat any in-chat card as a bonus status readout.
- ChatGPT Apps SDK submission has no published review-turnaround guarantee — don't gate a launch date on it.
- Work/Enterprise tiers default connectors and custom apps OFF pending admin action — a personal-account-only design will silently underperform on those seats.

## RESEARCH: upstream sync prior art

**Research value: high** -- concrete, load-bearing mechanisms exist for tracking upstream ideas without forking (structured deltas, differential/golden-file testing, cron-triage agents), but the specific pattern gbrain→brainz needs — an LLM watching one codebase and proposing ports into a different-language, different-substrate codebase — has almost no direct precedent; expect to assemble a novel pipeline from adjacent parts, not copy a known playbook.

### Prior art: automated upstream monitoring
Renovate/Dependabot generalizes only partly: the diff-and-open-PR loop needs a structured, versioned artifact (a lockfile pin) with a deterministic upgrade action. gbrain's "ideas" have no such artifact — a CHANGELOG entry is prose+code, not a version bump. What DOES generalize is Renovate's "Dependency Dashboard" pattern: one running issue with one row per pending item, so humans triage from a queue instead of drowning in N separate PRs.

Linux stable-backport offers two distinct mechanisms. The `Fixes:` tag is a structured pointer from a fix commit to what it fixes, letting tooling walk a graph without NLP. AUTOSEL, rewritten in 2025 around LLMs/embeddings, reads full diffs, messages, and historical backport patterns to recommend stable-tree backports even for untagged commits — the closest real analog to "an agent reads upstream commits and proposes downstream action," though it operates within one codebase on parallel branches, not across a language boundary. It ships an opt-out (`Cc: stable+noautosel@kernel.org`) — precedent for a manual "don't-port" marker.

Brave's Chromium rebase is periodic full-merge, not continuous idea-picking: every conflict-fix commit must cite the specific upstream CL, and unresolved issues get tagged `Chromium/Followup` so they don't block the rebase but aren't lost. AOSP vendor merges (LineageOS's `aosp-merger`) use the SAME architecture brainz already chose — patches over a manifest, not a full fork — but academic work (ACM TOSEM 2025) frames Android's merge-conflict-at-scale as unsolved, not routine. Distro packaging triage is candidly described (HN, Debian wiki) as manual burden that stops scaling once the patch count grows past a few thousand.

### Porting concepts across implementations
Differential testing — run identical inputs through N independent implementations, diff outputs, use a reference oracle or majority vote — is the technique that actually crosses substrate boundaries, because it needs no read of upstream source, only shared inputs and an oracle. It's proven at scale for compiler/engine correctness (JS-engine test transplantation, WebAssembly spec vs. Wasmtime vs. V8).

Golden-file/logic-test corpora are the most directly reusable pattern here: SQLite's `sqllogictest` format was lifted wholesale by CockroachDB as its primary SQL-compat suite — a plain-text, engine-agnostic input/expected-output corpus any new engine can run without touching the original C code. For gbrain→brainz this maps to a portable corpus of (operation-call → expected-shape) pairs derived from `src/core/operations.ts`'s ~110 ops, executable against brainz's Cloudflare implementation.

TCK-style spec+all-or-nothing-conformance bundles (Java) work only with a frozen spec and certification stakes tied to 100K+ tests — wrong shape for an upstream shipping multiple releases a week. Failure mode common to all of these: differential/golden-file testing tells you WHAT diverged, never WHY it's worth porting — it's a regression detector, not an idea-discovery tool. Something else still has to judge that a new `relational-recall.ts` semantics is worth porting.

### Agent-driven triage (2025-2026)
Real but thin, and mostly same-repo. GitHub's Agentic Workflows framework documents cron-triggered LLM agents that open issues/comments for human review; its own dogfood example (a daily Copilot-PR-analysis workflow) watches its OWN repo's agent-authored PRs and produces a digest, not code. ROCm/repo-digest (AMD, GitHub Actions + Claude Code) is the closest concrete precedent to the brainz shape: scheduled runs, per-commit sub-agents categorize by configured focus-areas/keywords, output is a ranked digest artifact rather than auto-applied code — but it still monitors its own org's repos; no public writeup of a cross-repo "watch upstream X, propose changes to downstream Y" agent surfaced in this search. Claude Code's scheduled cloud "routines" support exactly the needed cron+prompt shape (weekly changelog review is a named example use case), but this is infrastructure, not a validated methodology.

The only quantified numbers on bot-PR signal quality come from adjacent research, not this exact task: MSR 2026's "Circuit Breaker" paper finds simple structural features (diff size, files touched, config edits) predict review effort at AUC 0.957, and gating the riskiest 20% of PRs captures 69% of total review effort — evidence that cheap structural triage separates low- from high-cost bot output. The same corpus shows a bimodal pattern (28.3% instant-merge wins vs. a long tail of abandoned "ghosted" PRs) and reviewer-bot comment relevance DEGRADING as bot comment volume rises — a direct warning against a chatty, low-precision watcher. Be honest: this is closer to "primitives exist, adjacent research quantifies the failure mode" than "here is a proven playbook."

### Measuring drift
WPT/wpt.fyi + the Interop project is the strongest live example of a drift dashboard that stays used, and the mechanism is legible: a shared versioned test corpus (not each vendor's own tests), one published number per focus area that becomes a public/competitive score, year-scoped focus areas (Interop 2026: 15 new topics) so the corpus doesn't grow unbounded, and a named owner (a vendor coalition). Proof it works: the 2024 focus-area intersection score moved 48%→95%+ in one year because the number was visible and competitive. TCK/CTS-style all-or-nothing suites need a frozen spec and certification stakes — wrong fit here.

The generalizable failure mode (dashboard-abandonment literature) applies directly: a metric survives only with a named owner, a sub-minute parse time, and someone's incentives moving when it changes. An "operations implemented / operations total" ledger for gbrain-vs-brainz will decay like any unowned KPI unless it's wired into a workflow (blocks a release, feeds the weekly digest) rather than published and forgotten.

### Why downstream-tracking decays
ffmpeg/libav: a governance rupture (commit-access control + who owns the domain) made cooperation impossible even with identical code at fork time; FFmpeg kept absorbing Libav's work while Libav ignored FFmpeg — asymmetric absorption, not mutual tracking, and Libav went dormant by 2020. OpenSSL forks show divergence as explicit *policy*: BoringSSL's "live at HEAD" model forces continuous tracking (no maintenance branches, routine breaking changes) to stay close; LibreSSL diverges by deleting legacy surface, which structurally blocks re-convergence; QuicTLS deliberately narrows scope (just add QUIC) and stays close by refusing to diverge elsewhere. io.js/Node is the only full reconvergence here, and it happened because the split was pure governance (who controls the repo) — once Joyent ceded control to a neutral foundation, the trunk simply became io.js's repo renamed. Lesson: technical drift is recoverable; governance drift is what makes drift permanent — and gbrain/brainz have no governance conflict, which structurally favors staying in sync IF someone keeps funding the tracking mechanism itself. MySQL/MariaDB, Elasticsearch/OpenSearch, and Redis/Valkey are all license-driven splits where the fork explicitly commits to NOT tracking upstream's proprietary-adjacent surface — a different, business-boundary kind of divergence than brainz's voluntary, no-fork stance. Common thread: permanent divergence follows either a governance/legal incentive against reconverging, or the downstream simply stopping investment in the tracking mechanism — which nobody notices for a long time because there's no dashboard forcing the question.

### Practical cadence and artifact shapes
Cadence: weekly is the dominant real default (repo-digest, Claude's own "weekly changelog" example use case), batch-processing accumulated commits like AUTOSEL rather than reacting per-push — a good match given gbrain ships multiple releases/week. Input: prefer `CHANGELOG.md` entries plus `git log --stat` scoped to `src/core/operations.ts` and `docs/architecture/` over raw diffs — the operations contract file is gbrain's single highest-signal file to watch, since new/changed operations are its most portable ideas. Output: not auto-applied code (nothing found here auto-merges cross-repo semantic ports) and not one issue per idea (Renovate's own lesson: many small items overwhelm) — a single ranked digest issue, one row per candidate idea with a status (new/triaged/ported/rejected/wontport), matches the pattern shared by Renovate's dashboard, AUTOSEL's queue, and repo-digest's artifact. Noise control: gate on structural signal before spending semantic effort — mirror Circuit Breaker's finding that diff size/surface predicts cost; skip anything touching only tests/docs unless the CHANGELOG explicitly names a new capability. Human-in-the-loop budget: treat the digest as a capped review queue, not an obligation to triage everything — rank candidates and hard-cap human look-time (e.g., top 3-5/week), letting the rest age in the ledger for the next pass.

## SYNTHESIS

### surfaces: 1. One control plane, no read grant, one screen

**Description:** Split the server: `/mcp` serves the seven frozen tools to assistants; `/admin` serves connection state, billing, BYOK keys, context policy and export config to the web app — and its session credential is minted with **zero content-read scope**, asserted by a CI case that expects `scope_denied` on `recall`. Anything the dashboard shows *about memories* it gets by holding its own OAuth grant against the same `/mcp` endpoint, so the browser is literally another MCP client. Merged with the strongest half of the status idea: the one screen is not a dashboard but a ranked action list — deterministic collectors, `critical > warn > info` with a capped info tail, and **nothing renders unless a user action is attached to it**. Connection health is defined as *staleness against a declared cadence* ("nothing new from this source in 23 days — expected weekly"), never as an API ping returning 200.

**Basis:** `direct`. `src/core/operations.ts:794` — "FAIL-CLOSED: anything not strictly `ctx.remote === false` is untrusted"; `src/commands/serve-http.ts:2062-2064` hardcodes `remote: true` + `sourceId: tokenSourceId` for every HTTP caller, so a browser grant needs no new mechanism. Ranking model verified at `src/core/advisor/run.ts`: 9 deterministic collectors, `SEV_RANK = { critical: 0, warn: 1, info: 2 }`. Staleness vocabulary verified verbatim at `src/commands/integrations.ts:360` — "last event … exceeds max_age … the sense has stopped producing data."

**Rationale:** This is the only construction that makes "knowledge is consumed only over MCP" a property of the credential rather than a slogan with a dashboard-shaped exception, and it guarantees the web app can never display something an assistant couldn't retrieve. The action-list half prevents importing gbrain's operator SPA page list (`admin/src/App.tsx:10`: `'login' | 'dashboard' | 'agents' | 'log' | 'calibration' | 'jobs'`) into a consumer product where five screens replace one honest one.

**Downsides:** The idea's headline cost claim — "no second read API to build, secure, or keep warm" — is **false as written**, and the verifier was right. gbrain's `serve-http.ts` runs exactly 20 `/admin/api/*` endpoints (agents, sources, stats, full-stats, health-indicators, jobs/watch, calibration ×3, requests, api-keys ×3, register/rescope/revoke-client, issue-magic-link, sign-out-everywhere). Every one is non-content but all of them must still exist. This shrinks the privileged read API; it does not eliminate it, and pitching it as free will cost you the meeting. Second, the worked example doesn't survive the schema: `recall`'s `total` (`RESPONSE_SCHEMAS.recall`, required `['facts','total','protocol_version']`) is query- and budget-scoped, so a brain-wide item count is **not** obtainable "by being an ordinary MCP client" — it needs an MCP resource (allowed by decided direction #6) or an eighth tool (not allowed). Decide which before building the empty state. Third, the staleness half presupposes sources that declare a cadence at connect time; brainz has no ingestion substrate yet, so v1 cadence applies only to what exists (file/folder sync, export destinations, device pairing), not to Gmail/Notion.

**Note on one verifier objection I overrule:** the verdict dinged this (and two other ideas) for saying "seven frozen tools" when "the repo says five everywhere." The repo does say five (`src/core/verbs.ts:31` — `VERB_NAMES = ['recall','remember','entity','synthesize','forget']`), but decided direction #6 says *seven MCP tools = 5 memory verbs + ChatGPT's mandated `search`/`fetch`*. The ideas were counting brainz's surface, not gbrain's. That objection is void wherever it appears.

**Confidence:** 82%
**Complexity:** Medium

### surfaces: 2. First value before first OAuth — and the connect prompt rides the failure envelope

**Description:** The empty state is not a connector grid. It is one act: tell the assistant one thing about yourself. The install flow ends inside the chat client, so `remember` fires there, the status panel lights, and `recall` returns it seconds later — target is first stored-and-retrieved memory in under 60 seconds with zero third-party consent screens. Connectors are offered only *after* the loop has been felt, and never through a `connect_source` tool: when `recall` returns empty or flags `search_degraded`, the response envelope carries a `setup` block — one human sentence plus a single-use, short-TTL claim URL bound to the caller's grant. On desktop and mobile, where clicking a chat link is unreliable, the same claim renders as a six-character pairing code plus QR, typed at an already-authenticated `/link` page. This merges three independent inventions of the same mechanism (connect handoff, seat claim, raise-the-cap link) into one primitive.

**Basis:** `external` + `direct`. The gate is external and dated: Gmail-class restricted scopes require a Google-empanelled CASA Tier 2/3 assessment, re-certified every 12 months on a multi-week timeline — a genuine go/no-go on any zero-config mail connector, and the only candidate whose external citation is present in the grounding's research layer. Repo-side, the agent-mints/human-redeems-out-of-band handoff already exists: `src/commands/serve-http.ts:1197` `POST /admin/api/issue-magic-link` (bearer bootstrap token → one-time nonce) redeemed at `GET /admin/auth/:token` (`:1218`, single-use, TTL'd, rate-limited 10/min/IP). Adding a `setup` field is legal under the frozen protocol: `src/commands/protocol.ts:104` — `versioning_policy: 'additive-forever: … new optional fields/params may be added'`.

**Rationale:** It decouples launch from a certification the team does not control, and it inverts the funnel so the memory loop is experienced before mailbox access is requested — the only sequencing under which that grant is a reasonable ask. Routing the handoff through the result envelope costs zero tools and zero system-prompt tokens, which is the only way a connect prompt coexists with the seven-tool freeze.

**Downsides:** The magic-link precedent is weaker than it reads: it is operator-dashboard login (bootstrap token → cookie session), **not** a third-party OAuth consent handoff, and gbrain has zero OAuth data connectors today. So the pattern ports, the connector does not. Second, the whole shape presupposes brainz builds OAuth connectors at all — the grounding lists them only under "would be new," not as a decided roadmap item; if the answer is "file/folder sync forever," the CASA argument is moot and this collapses to plain onboarding advice. Third, the supporting institutional-learning citation (`src/core/init-embed-check.ts:129`, front-load the embedding-key check) argues for *front-loading a check*, which is the opposite of *deferring a setup step* — it's decorative, not load-bearing; don't cite it in the room. Fourth, "sync takes tens of minutes" has no repo citation and shouldn't be used as the urgency argument.

**Confidence:** 78%
**Complexity:** Low

### surfaces: 3. Two grants, one brain — the work connector reads work-origin only

**Description:** In ChatGPT Work the admin approves one connector per workspace and tool definitions freeze at approval, so connector identity cannot be per-user. Separate the two acts: **the admin approves the connector; each employee claims a brain.** First call from an unclaimed seat returns a `scope_denied`-shaped envelope carrying a claim URL (the same primitive as #2); redeeming it binds an OAuth grant to that individual. The grant issued through the *work* connector is minted with read access to `origin: work` only, so the personal half is structurally invisible from the employer-approved path rather than filtered in UI. The user's personal Claude Desktop connector holds a second grant reading both. One brain, one file tree, two grants, two views — and the employer's admin console carries the same zero-read grant as the consumer dashboard.

**Basis:** `reasoned`, with a verified mechanism analog. gbrain's grant model already carries the two fields this shape needs — `AuthInfo.sourceId` for write authority and `allowedSources[]` for read federation (`src/core/operations.ts:479-522`), populated from `oauth_clients.federated_read` / `source_id`, and enforced through `sourceScopeOpts(ctx)` on every read-side op per CLAUDE.md's source-isolation invariant. The origin stamp itself is decided direction #3.

**Rationale:** A personal-account-only design silently underperforms on exactly the seats that pay, and "we filter work vs personal in the app" is the kind of UI-level tenancy claim that does not survive a security review. Fencing at grant-issue time makes the separation a property of the credential, and it is the only candidate that gives the binding user constraint ("personal and work info in the same place, just mark it as such") an actual mechanism instead of a field.

**Downsides:** The verifier called this **refuted** because `origin: work` appears nowhere in gbrain and CLAUDE.md documents exactly two axes (brain, source). That grep is correct about gbrain and wrong about the premise — the origin stamp is decided direction #3, handed down in the constraints, not a claim about the reference repo. But the *repaired* version still carries real cost the original pitch hid: `allowedSources[]` fences by **which repo**, not by an origin tag *within* a source, so this needs a genuinely new grant field (`allowedOrigins[]`) plus a new fence site in `sourceScopeOpts` — you inherit the pattern, not the code. Second, the lead sentence attributes ChatGPT Work's approval-freeze semantics equally to Claude Enterprise; only the ChatGPT Work behavior is sourced. Third, and unpriced anywhere: one-brain-across-both means employer-relevant content lives in a consumer-owned per-user D1, which collides with data residency, legal hold, and employee-offboarding expectations — the security story is clean, the *legal* story is not. Fourth, since origin must be credential-derived and immutable, a mis-stamped item is unfixable by the user by design; you need an explicit re-stamp path or support tickets will be your product.

**Confidence:** 61%
**Complexity:** High

### upstream: 1. Be gradeable over the wire before you're gradeable on the bench

**Description:** gbrain ships a conformance runner that speaks to **any** MCP endpoint: `gbrain protocol conformance --target https://… --token <tok>` connects over `StreamableHTTPClientTransport`, calls `listTools`, exercises each verb, and emits a JSON report against `RESPONSE_SCHEMAS` + `ERROR_SCHEMA` (`src/commands/protocol.ts:130-200`). brainz points it at its own hosted `/mcp` in week one and gets contract conformance for **zero adapter code** — a CI job, not a project. That is the cheap half. The expensive half is BrainBench: vendor `evals/brainbench/{fixtures,gold,schema}` at a pinned `fixtures_hash`, write one `brainz` adapter against `adapters/shared.ts`, and run the four suites (know-to-ask, push precision/recall, write-back fidelity, continuity). Ship them in that order and never conflate them. The second-order payoff stands either way: "are we behind?" reduces to diffing one string, because when gbrain's maintainers move `fixtures_hash` they have decided a behavior is durable enough to grade.

**Basis:** `direct`. All corpus citations verified: `evals/brainbench/_ledger.json` — `generated_fixtures: 135`, `holdout_fixtures: 23`, `gold_turns: 241`, `generation_cost_usd: 0`, `gold_validation.agreement: 0.964`; four adapters exist (`claude-code.ts`, `codex.ts`, `openclaw.ts`, `shared.ts`); four JSON schemas in `evals/brainbench/schema/`. The conformance transport is verified in `src/commands/protocol.ts` (this is the artifact the "four artifact classes" idea *should* have cited — see Downsides).

**Rationale:** Every other tracking mechanism proposed across both lanes is prose that decays; this one fails a build. And it splits cleanly into a week-one artifact and a quarter-scale one, so the lane produces a green/red signal long before the bench is affordable.

**Downsides:** Three corrections the original pitch needs. (1) The claimed double duty — `source_isolation_violations` as "continuous proof of per-user isolation" — **misreads its own source**. `docs/eval/BRAINBENCH.md:52` discloses that detection is *slug-keyed* cross-**source** leakage inside one shared brain DB, and explicitly defers same-slug content leaks to a separate engine-layer fuzz. brainz's isolation claim is cross-**tenant**, across physically separate D1 databases; this metric cannot exercise that boundary and gating it at zero proves nothing about the thing the hosted security story rests on. (2) "Write ONE adapter" hides that `claude-code`, `codex` and `openclaw` are all thin wrappers over the *same* gbrain engine, differing only in injection shape. A brainz adapter needs an independent extraction, write-back and entity-resolution engine on D1+Vectorize before fixtures produce non-trivial scores — months, not a week-one shim. (3) Vendoring the corpus and tracking `adapters/shared.ts` reintroduces a code-level coupling to a repo the constraints call reference-only; pin the hash and accept lag, or you have a soft fork.

**Confidence:** 84%
**Complexity:** Medium (conformance) / High (BrainBench adapter)

### upstream: 2. Read the changelog, not the code — bootstrap backwards, gate forward

**Description:** Two mechanisms, one insight. **Bootstrap:** run `CHANGELOG.md` newest-to-oldest, collapsing supersessions, producing a dated concept snapshot pinned to a commit SHA — because the changelog is hundreds of releases of already-distilled rationale authored by the person who made the decision, in a stable shape (plain-English headline, before/now table, "Things to watch:", `## To take advantage of vX`, and `### Itemized changes` with one path-scoped bullet per file). The code tells you what; this is the only place the why survives. That SHA turns the ongoing watcher into a pure delta job with a resumable cursor. **Gate:** each week, intersect the release's touched paths against `RETRIEVAL_WATCH_PATTERNS` ∪ a brainz-owned set (`src/core/verbs.ts`, `src/mcp/surface.ts`, `docs/protocol/MEMORY_VERBS_v1.md`, `src/core/migrate.ts`, `evals/brainbench/**`, `scripts/check-*.sh`); only survivors get semantic reading. The bootstrap runs under a hard spend cap, chunked per release, estimating before running and refusing over budget.

**Basis:** `direct`. `CHANGELOG.md` = 23,231 lines vs `src/core/operations.ts` = 6,449; v0.44.1.0 verified to carry exactly the claimed section shape. `src/core/eval/drift-watch.ts:5-11` verified verbatim: "Too narrow … misses real regressions like a chunker change. Too wide … trains the operator to ignore the warning," plus "Adding to this list REQUIRES a CHANGELOG line so coverage grows deliberately." Cost discipline is grounded in `docs/incidents/2026-05-20-lsd-cost-explosion.md` — $50.71 against a $0.96 estimate (53×), far-set selection pulling 1,985 items instead of 12, no mid-run circuit breaker, judge call overflowing context.

**Rationale:** gbrain ships multiple releases a week; an undifferentiated firehose is the documented death of this kind of watcher. Structural gating before semantic spend is the correct shape, and the changelog already contains the reasoning the watcher would otherwise reconstruct from diffs at many times the tokens.

**Downsides:** The seductive part — "watch `drift-watch.ts` itself, so the filter self-updates from upstream governance" — is much narrower than pitched. I read the file: `RETRIEVAL_WATCH_PATTERNS` has **six** entries, all retrieval-quality (`src/core/search/`, `embedding.ts`, `chunkers/`, two AI recipes, `operations.ts`). Nothing about auth, security, or schema — `oauth-provider.ts`, `migrate.ts`, and the engine files, which CLAUDE.md itself flags as the highest-stakes surfaces, are unwatched. The brainz-owned half of the union does **not** inherit the self-updating property, so the headline claim holds only for the retrieval slice. Second, "collapsing supersessions" across the full 23,231-line corpus is itself an unbounded cross-referencing task with no chunking strategy given — the exact context-overflow failure mode (RC3) the idea claims to have learned from. Third, both source ideas cite external precedents (arXiv 2601.00753 for structural pre-gating; AUTOSEL for batch processing) that are absent from the grounding's research layer; the mechanism stands on the repo evidence alone, so drop them rather than defend them.

**Confidence:** 76%
**Complexity:** Medium

### upstream: 3. Every "not yet" is an artifact with an expiry date

**Description:** One ledger, two populations, one artifact shape. `upstream/concepts.jsonl` holds a row per gbrain concept — `implemented(where)` | `omitted(reason_code, revisit_by)` | `not-yet(priority)` — and CI fails when a watcher-detected concept appears in none of the three. Two additions make it not decay. **`revisit_by` is mandatory on every omission and CI fails when it passes**, because brainz's omissions are overwhelmingly "not on this substrate *yet*," and every constraint that would drive one is a moving number. **`reason_code` is a closed vocabulary** (`substrate:no-bm25`, `substrate:worker-mem-ceiling`, `product:consumer-not-operator`, `policy:frozen-tool-surface`), so after thirty omissions the ledger becomes a queryable design-constraint corpus and "eleven omissions trace to one ceiling" is a substrate-migration argument produced as a byproduct of saying no. The hazard corpus lands in the same table: each `scripts/check-*.sh` becomes a row with `{failure_mechanism, what_masked_it, brainz_analog, guard, status}`, and every unported one ships as a **skipped test with a reason string**, so the suite prints the unguarded-hazard count on every run.

**Basis:** `direct` for the corpus, `reasoned` for the mechanism. 42 `scripts/check-*.sh` guards exist. `scripts/check-worker-lock-renewal-shape.sh:7-9` — "Production lost ~39 worker processes/day to this exact shape when PgBouncer rotated connections during a `renewLock` call"; `:25` — "Intentionally bug-pattern-specific, not implementation-specific." `scripts/check-jsonb-pattern.sh:5-8` records the v0.12.0 silent-data-loss bug where "JSONB columns stored as string literals on Postgres while PGLite hid the bug." The translations that fall out are concrete: dev-engine-masks-remote-engine → parity test that must run against remote, not local; unhandled rejection in a detached timer → uncaught async in an alarm handler; `check-progress-to-stdout.sh` → anything non-JSON-RPC on the MCP stdio stream, the most common way a local MCP server dies silently.

**Rationale:** The single most likely failure across this whole lane is not porting the wrong thing — it is brainz quietly stopping and nobody noticing for a year. A passed date is the only forcing question a build can ask. Merging the hazard cards into the same ledger means the mechanism that keeps the lane alive is also the mechanism that delivers its most concrete value, so neither can be abandoned separately.

**Downsides:** The hazard half's schema is thinner than advertised, and I checked: across all 42 guards, only **2** contain masking language (`hid`/`masked`) and **1** carries a quantified production cost. The two showcased scripts are the two best in the corpus, so most cards ship with `what_masked_it` and the cost field empty — real value, one-afternoon bootstrap, but not "39 more of these." Second, every concrete translation presupposes a Cloudflare/D1/Durable-Object target, which the grounding treats as candidate-substrate research with live disqualifiers, so card *content* may not survive a substrate decision even though card *shape* will. Third, the ledger is the most process-shaped thing in this document and therefore the most abandonable: if the CI date-check is ever made non-blocking "just for this sprint," the whole mechanism is decorative within a month. Fourth, the divergence prior art the original pitch leaned on (LibreSSL/BoringSSL, MySQL/MariaDB, Libav, AUTOSEL) is absent from the grounding entirely — the argument survives on the substrate-numbers-are-moving point alone, which is sufficient; don't reach for the analogies.

**Confidence:** 68%
**Complexity:** Low

### Cross-cutting combinations

**The claim URL is one primitive with four callers, and it is what makes the seven-tool freeze survivable.** Four separate ideas independently invented the same thing: connect-a-source (surfaces #2), claim-a-seat from an unclaimed enterprise connector (surfaces #3), raise-the-cap when `synthesize` hits `BudgetExhausted` (cut idea #7), and log-in-to-the-dashboard (`serve-http.ts:1197`). All four are "the assistant hands a human a single-use, short-TTL, grant-bound URL that redeems in a top-level browser context." Build it once, as an optional `setup` field on the shared error/result envelope — legal under the verified `additive-forever` policy — and every future capability that needs a human in the loop gets a delivery channel that costs zero tools and zero system-prompt tokens. This is the mechanism that lets direction #6's freeze hold for years instead of quarters.

**Conformance-over-the-wire is a *surfaces* artifact wearing an upstream badge.** `gbrain protocol conformance --target https://… --token` requires nothing from brainz except that its hosted `/mcp` speaks streamable HTTP and honors bearer auth — which is precisely surfaces #1's split-server shape. So the same architectural decision that makes the control plane read-scopeless also makes brainz externally gradeable by upstream's own harness on day one. Run it twice per CI: once with the assistant grant (expect full pass) and once with the **dashboard** grant (expect `scope_denied` on every content verb). That single job proves the seven-tool contract and the zero-read-grant claim simultaneously, and it is the honest replacement for the `source_isolation_violations` double-duty claim that BrainBench cannot actually deliver.

**The upstream ledger should be the register from decided direction #1.** Direction #1 already commits to publishing "a register of every component touching >1 user." Upstream #3 already commits to a machine-readable ledger with a closed reason-code vocabulary and CI enforcement. These are the same table with different `kind` values — `shared-component`, `omission`, `hazard`, `concept`. One table, one CI check, one publishing pipeline; the isolation register gets the expiry discipline for free (a shared component with no `revisit_by` is how multi-tenancy creeps back in), and the upstream ledger inherits an external audience, which is the cheapest available defense against it going quiet in month four.

### Contradictions with already-decided directions

- **`prove_isolation` (direction #1) vs. seven frozen tools (direction #6).** Direction #1 calls it a *verb*; direction #6 freezes the tool list at five verbs + `search`/`fetch`. An eighth tool breaks the freeze at the moment of shipping. Resolution: ship it as an MCP **resource** or as an argument on an existing verb — decide now, because direction #6 explicitly reserves resources for exactly this.
- **Dashboard content reads (surfaces #1) vs. direction #6.** Verified: `recall`'s `total` is query- and budget-scoped, so a brain-wide inventory count is unreachable through the frozen seven. Every consumer dashboard number ("2,140 memories") is therefore either an MCP resource or a new tool. Same fork as above; resolve both together.
- **Live isolation receipt on page load (cut idea #6) vs. near-zero idle cost + isolation.** Running `prove_isolation` per dashboard visit means deliberately generating cross-tenant authz failures at consumer traffic volume, on the hot path, with compute per visit and a permanent stream of denied-access entries in your own audit log. Batch it to the canary tenant and serve a cached, timestamped result; don't probe per pageview.
- **Delete-derived-data-on-revoke (cut idea #6) vs. `forget`'s semantics.** `src/core/verbs.ts:295` — "The fact is expired (audit trail kept), not deleted." A revoke path that hard-deletes and a `forget` verb that never deletes are two deletion semantics in one product; users will hit both. Direction #5 makes the hard-delete cheap (derived data is rebuildable from files), so the conflict is resolvable — but it must be an explicit decision, not an emergent one.
- **Gateway-enforced spend caps (cut idea #7) vs. "security is critical, isolation is key" + BYOK.** Getting per-user-ID caps from a vendor gateway requires routing the user's own provider key and raw prompt text through a third-party proxy. gbrain's actual gateway (`src/core/ai/gateway.ts`) instantiates native providers with the user's key and no `baseURL` — direct to provider. For a personal-brain product, "your memories transit our AI vendor's proxy so we can meter you" is a privacy regression traded for a billing convenience. Name the trade before adopting it.
- **BrainBench adapter (upstream #1, second half) vs. "gbrain is reference only, not a dependency, not a fork."** Vendoring fixtures at a pinned hash is clean. Writing an adapter against `adapters/shared.ts` and keeping it green as that pipeline moves is a code-level coupling — a soft fork with extra steps. The wire-level conformance runner has no such coupling, which is the real argument for shipping it first.
- **Origin-fenced work grant (surfaces #3) vs. one-D1-per-user (direction #1).** Direction #1's isolation unit is the *person*. Direction #3's fence is the *origin*. Together they place employer content inside a consumer-owned database — technically sound, legally unexamined (residency, legal hold, offboarding). Not an engineering contradiction; an unowned product decision.
