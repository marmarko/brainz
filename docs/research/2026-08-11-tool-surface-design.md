## GROUNDING: what MCP primitives clients actually support

**Research value: high** -- this determines whether "ship new capability as MCP resources instead of new tools" is a viable freeze-preserving strategy, or a strategy that only works for half the target clients.

### Resource support, per client

| Client | Resources discovered | Model-initiated | Templates |
|---|---|---|---|
| **Claude Desktop** | Yes, but only via explicit UI attach — "Click the '+' button on the bottom of the chat box... then select 'Connectors'" (support.claude.com). No documented path for the model to read a resource the user hasn't attached. | **No** — user-initiated only, on current evidence | [unconfirmed] |
| **Claude Code** | Yes, fully. `resources/list`/`resources/read` are discovered at connect time; users reference resources via `@server:protocol://resource/path` autocomplete (code.claude.com/docs/en/mcp) | **Yes** — "Claude Code automatically provides tools to list and read MCP resources when servers support them" (same doc). This is directly verifiable: my own tool list in this session includes `ListMcpResourcesTool`, `ReadMcpResourceTool`, `ReadMcpResourceDirTool` — Claude Code turns the resources primitive into ordinary model-callable tools. | Supported — the `@server:proto://path` addressing matches `resources/templates/list`'s URI-template design |
| **ChatGPT (standard)** | Not documented as the MCP resources primitive at all. OpenAI's compatibility layer only discusses `search`/`fetch` tools (developers.openai.com/api/docs/mcp) | N/A — resources primitive not exercised | Not found |
| **ChatGPT Work/Enterprise** | Same as above | N/A | Not found |

The spec itself (2026-07-28) frames resources as **"application-driven, with host applications determining how to incorporate context based on their needs"** — automatic model-initiated inclusion is *permitted* but explicitly optional, alongside a picker UI or search. Nothing mandates model-initiated access. So it's a per-client implementation choice, and only one of the four target clients (Claude Code) made that choice.

### Prompts, per client

Spec text is unambiguous and identical across every revision including 2026-07-28: **"Prompts are designed to be user-controlled... Typically, prompts would be triggered through user-initiated commands in the UI... as slash commands."** Claude Code implements this literally — `/mcp__servername__promptname`, discovered via `/`, arguments space-separated, "prompt results are injected directly into the conversation." No client in this set exposes prompts to the model for autonomous invocation; none was expected to, by design. ChatGPT's docs don't mention the prompts primitive at all. Claude Desktop's is [unconfirmed] but the spec's design intent plus Desktop's attach-only pattern for resources makes user-initiated-only the reasonable read.

### Output schemas and annotations

**Output schemas exist and are current.** 2026-07-28 keeps `outputSchema` + `structuredContent`, and this revision *loosens* them (SEP-2106: "any JSON Schema 2020-12 keywords" allowed, `structuredContent` now "any JSON value"). Servers **MUST** conform, clients **SHOULD** validate. This is real and load-bearing for reducing tool proliferation — a single verb can return richer structured shape without a new tool name.

**Annotations, confirmed from the live schema** (`ToolAnnotations`): `title`, `readOnlyHint` (default false), `destructiveHint` (default true, meaningful only when `readOnlyHint==false`), `idempotentHint` (default false), `openWorldHint` (default true). No successor fields, **no cost/spend annotation exists in the spec** — confirmed absent from the current schema. The spec itself warns clients to treat annotations as **untrusted unless from a trusted server** — i.e., don't gate real security decisions on them.

Whether clients *act* on them is weaker evidence. ChatGPT's docs show real write-gating behavior ("ChatGPT currently requires manual confirmation in any conversation before write actions can be taken"; a read-only-only compatibility server "skips approval for those tools") — but the doc text never names `readOnlyHint` as the mechanism, so the causal link to the standard annotation is **[unconfirmed]**, not just inferred convention. Claude Code has its own proprietary superset for consent-gating (`_meta["anthropic/requiresUserInteraction"]`, forces a prompt on every call, no "don't ask again") — evidence Anthropic didn't consider the four standard hints sufficient signal for real consent/cost gating and built past them. No client anywhere keys on a "this costs money" signal — it doesn't exist in-protocol.

### The search/fetch mandate and the approval freeze

Confirmed current and unchanged in substance from your framing. OpenAI's docs: **"your MCP server should implement two read-only tools: `search` and `fetch`, using the compatibility schema."** `search`: single query string in → `{results:[{id, title, url}]}`, dual-encoded as `structuredContent` + JSON text. `fetch`: id string in → `{id, title, text, url, metadata?}`, same dual-encoding requirement.

The admin-approval-freeze mechanics (list-only vs. full-schema, and whether per-client tool-set variance is acceptable to review) were **not found** in the primary docs I could reach — OpenAI's public MCP page doesn't address enterprise-approval internals at all. Treat the freeze granularity as **[unconfirmed]** beyond what you already know operationally; I could not independently corroborate it from developer-facing docs.

### Per-client tailoring

No explicit "vary tools by client" guidance found in the spec or in any client's docs — it's neither blessed nor called out as anti-pattern in what I could reach. But the spec structurally assumes per-request variance is normal: `tools/list` results **"MAY vary by the authorization presented on the request — for example, returning only the tools the caller's granted scopes permit — since credentials are per-request input, not connection state"** (identical clause repeated for resources and prompts). Combined with 2026-07-28's stateless redesign — every request now carries `io.modelcontextprotocol/clientInfo` in `_meta`, and clients "SHOULD identify themselves on each request" — a server has both the signal (client identity, every call) and spec-sanctioned precedent (scope-based list variance) to legitimately serve a different tool set per caller. Whether OpenAI's review process specifically accepts a *ChatGPT-targeted* subset differing from a *Claude-targeted* subset is **[unconfirmed]** — no review-policy doc surfaced.

### Tool count vs accuracy — what is actually measured

Vendor guidance found is **qualitative, not quantitative**. Anthropic's own tool-design writeup: *"More tools don't always lead to better outcomes... too many tools or overlapping tools can also distract agents from pursuing efficient strategies,"* recommending "a few thoughtful tools targeting specific high-impact workflows" over exhaustive API coverage — no threshold number, no benchmark cited. Cursor's documented 40-tool hard cap (from your framing) is a product decision I could not find accompanied by published accuracy research on their docs — treat the *cap* as confirmed-by-product-behavior but its *justification* as **[unconfirmed]**. gbrain's own functional-area-resolver eval (+13–17pp for hierarchical dispatch at 48% size) is real internal evidence but — as your prompt already notes — it measured markdown routing tables, not live MCP `tools/list` selection, so it's suggestive, not proof, for this decision.

### What this means for a resources-as-growth-channel strategy

**It doesn't hold uniformly, so it can't be the sole strategy.** Concretely:

- **ChatGPT (both tiers, ~half the target surface):** resources are functionally absent. The mandated `search`/`fetch` pair is OpenAI's *own* reinvention of "discover + read a resource" as tools — which is itself evidence that when OpenAI needed exactly this capability, they shipped it as tools, not resources. Any brainz capability that must reach ChatGPT users has to be a tool (or ride inside `search`/`fetch`'s existing shape) regardless of what the freeze allows.
- **Claude Desktop:** resources exist but are user-gated (paperclip/picker) — the model can't reach them unprompted, so they don't work as a *silent* capability-growth channel; a user has to know to attach the thing.
- **Claude Code only:** resources are genuinely model-initiated, proven directly by this session's own tool list (`ListMcpResourcesTool`/`ReadMcpResourceTool`). But note the mechanism — Claude Code exposes resource access *as tools anyway*. The "no new tool names" freeze is preserved at the MCP-server-manifest level, but the effective client-side surface still grows by exactly the same kind of entry point.
- **Prompts are a dead end for growth** everywhere — spec-mandated user-only, confirmed in every client checked.
- **Panel writes (SEP-1865) still need `tools/call`** — nothing in resources or prompts substitutes for a write action; this genuinely does force either new tool names or overloading verb args, independent of the resources question.

Net: "ship growth via resources" is real and works for Claude Code's model-reachable case, is inert for prompts, and is moot for ChatGPT, where the two mandated tools already absorbed the resource-like use case into the tool surface. A strategy that assumes uniform resource support across all four clients will silently under-deliver on two of them.

## REVISED DESIGN

### Title

**Nine names on the wire, seven in front of any model**

### Description

The old card froze a number it never derived. Replace it with a rule that derives one. **A capability earns its own tool name only when (a) its *response contract* cannot be a variant of an existing tool's, or (b) something outside the model — a client's consent UI, an enterprise admin, or a protocol mandate — gates on it per-tool.** Everything else ships as an optional argument, a response field, or connection state. Test (a) applies to the *response*, not the input: input schemas absorb anything, response contracts do not. Test (b) is law rather than taste, because MCP attaches `readOnlyHint`/`destructiveHint`/`idempotentHint` and every client's write-gating **per tool** — there is no per-argument annotation and no cost annotation anywhere in the 2026-07-28 schema. Two capabilities needing different consent, annotation, or admin scope structurally cannot be one tool.

Run that rule against the jobs and it produces **nine names on the wire, seven advertised to any model, one no model is meant to see.** Not seven-because-inherited. `recall` and `search` are one job wearing two names for disjoint audiences; `manage` is dispatch-only. At 550–1,400 tokens per definition, seven is 3.9k–9.8k of system prompt — an order of magnitude under Cursor's 40-tool cap, which was never the binding constraint. Per-client token load was.

**The surface is selected by endpoint, not by `clientInfo`.** This is the load-bearing correction. `io.modelcontextprotocol/clientInfo` is self-reported and, per the spec, clients only *SHOULD* send it — sniffing it to decide whether to advertise `search`/`fetch` means one missing header outside Developer Mode gets the connector rejected outright. So brainz publishes two connector URLs and the user picks at install: `https://mcp.brainz.app/mcp` (Claude Desktop, Claude Code, Cursor, anything unknown — the portable default, which also advertises `search`/`fetch` as aliases so a misrouted ChatGPT install still works) and `https://mcp.brainz.app/openai` (ChatGPT and ChatGPT Work). The OAuth grant binds to the endpoint. `tools/list` results "MAY vary by the authorization presented on the request" — that clause covers a per-grant surface; it does not cover a per-claimed-identity one. `clientInfo` survives only as telemetry. The honesty invariant is testable and CI-enforced: **for a given authenticated identity, every read and write of memory is reachable from every endpoint; only names and shapes vary.** `search(q).results[].id` must equal `recall({query:q}).results[].id` in order, and `fetch(id).text` must equal `recall({id}).content` — one handler, two projections, never two retrieval stacks. gbrain has the scar tissue for why: `paramDefToSchema` exists in `src/mcp/tool-defs.ts` because three inline schema mappers drifted and the live HTTP path silently dropped `items` for a release.

**`synthesize` does not survive.** Two of three lanes kept it; I'm cutting it, and the argument is economic rather than aesthetic. It is the only verb whose marginal cost lands on brainz instead of the caller, and its cost scales with the user's corpus while a *model's judgement* decides when to spend it. gbrain has already paid for that exact shape: `docs/incidents/2026-05-20-lsd-cost-explosion.md` records "$50.71 actual vs $0.96 estimated — 53× over estimate." The briefing decision removed its flagship use; the caller already has a frontier model with the whole conversation in context, which brainz's server-side model does not; and a seconds-to-minutes blocking `tools/call` on a protocol that retired sessions has no retry story that doesn't re-spend. gbrain's own description prefix says the quiet part: `'[EXPENSIVE / SLOW — makes LLM calls, seconds-to-minutes latency, costs money] '`. The capability is real and moves to the **nightly consolidation schedule** — same money, spent where it can be estimated before running, capped mid-run, and amortised across every future `briefing` read. If on-demand deep research earns its way back, it returns as an async start→id→collect pair, which is a new response contract and therefore honestly a new name under the trip-wire. Keep `synthesize` dispatchable-but-unadvertised, returning `unavailable` with `suggestion` pointing at `briefing`, so a caller carrying the frozen five gets an actionable error instead of `unknown_tool`. Consequence stated plainly: brainz does **not** pass gbrain's certifier, which asserts all five verbs are advertised plus `synth?.description?.startsWith('[EXPENSIVE')` at `src/core/verbs/conformance.ts:182`. brainz declares `memory-verbs-v1-partial` and publishes the delta rather than pretending.

**`prove_isolation` and inventory counts live in `brain`, and the attestation *also* rides `_meta` on every response.** These are not redundant; they have different consumers. The unconditional `_meta["brainz.app/brain"]` stamp — Neon project id, database, storage prefix, signature, timestamp, plus counts and `definitions_digest` — is the stronger trust artifact, because an attestation you have to ask for proves a claim while one stamped on every single response is a property. But `_meta` is invisible to the model, so a user asking Claude "is my data actually isolated?" gets nothing from it. `brain` is the model-reachable rendering. It earns its name three times over: it is the only route that reaches ChatGPT users deterministically (resources are functionally absent there, and Lane 1's "search will surface a virtual document" is unproven by its own admission); it is read-only, so the trust claim survives ChatGPT Work's writes-off-by-default posture exactly where enterprises need it; and brain-wide counts are genuinely unreachable through `recall`, whose `total` is query- and budget-scoped. Do **not** hang counts on bare `recall()` — that shape already means something in the reference implementation (`listFactsSince(sourceId, new Date(0), ...)`, the recent-facts feed), and stacking three intents on one trigger is the drift the envelope rules exist to prevent.

**Panel writes live in `manage`, reversible-only, nonce-gated, advertised to nobody.** An MCP Apps view (SEP-1865) calls back via `tools/call` over the *parent* connection, so `manage` is dispatchable on `/mcp` but excluded from `/mcp`'s advertised list — gbrain's two-layer pattern (`filterOpsForSurface` + `allowedOpNames` in `src/mcp/surface.ts`) inverted: hidden from `tools/list`, allowed in dispatch when the call carries the short-TTL `panel_nonce` minted into the panel HTML at `resources/read` time. The action enum is `set_context_policy | set_spend_cap | pause_source | resume_source` — **reversible actions only**. Disconnect, delete, export and sharing deep-link to the web app with a signed URL. That removes the catastrophic actions instead of annotating around them, which is what lets `destructiveHint: false` be honest and keeps the confirmation prompt meaningful elsewhere. An action-enum dispatcher is an anti-pattern when a *model* must choose the action and correct when deterministic iframe code does. **Unresolved and stated as such:** whether hosts forward `tools/call` for a name absent from `tools/list` is [unconfirmed]. If they refuse, `manage` becomes the eighth advertised tool on `/mcp` at ~700 tokens and is safe anyway — a model has no nonce and gets `invalid_params`, and the enum contains nothing worth reaching. That is the accepted cost of an unconfirmed assumption, not a fix.

**The growth channel, honestly: resources are not one.** Drop the claim entirely. On both ChatGPT tiers the resources primitive is functionally absent — and OpenAI's decision to reinvent "discover then read" as `search`/`fetch` *tools*, in a spec that already had resources, is the strongest evidence available. On Claude Desktop resources are user-attach-only, so the model can't reach them unprompted. On Claude Code they are genuinely model-initiated — but Claude Code implements that by re-exposing them as tools (`ListMcpResourcesTool`/`ReadMcpResourceTool`), so the manifest stays frozen while the effective entry-point count grows identically. That's accounting, not saving. Prompts are user-controlled by spec everywhere. Use resources for exactly one thing: the SEP-1865 panel view, which the spec requires to be a resource. The real ladder, in order: **optional argument → connection state → response envelope → unadvertised panel action → a new name.** Note the asymmetry that makes this non-obvious: arguments are free on three clients and *not* free on ChatGPT Work, where a new optional param is a definition change requiring an admin re-scan; the **response envelope is the only channel free on all four**, precisely because responses are not part of the definition an admin approves. So the enterprise operating rule is **put growth in responses, batch request-schema changes into dated releases.** The envelope is closed at seven keys — model lane: `protocol_version`, `degraded`, `notice[]` (≤2), `next[]` (≤3 `{tool, args, why}`), `setup`; client lane: `brainz.app/brain`, `brainz.app/setup_url` — with two rules that keep it from becoming a hidden API: a field must be true *independent of the request* (if it needs `include_foo:true`, it belongs in `outputSchema`, not the envelope), and every `next[].tool` must be advertised **on that endpoint** with every `args` key in that endpoint's schema, or the discovery channel teaches models to call things that return `unknown_tool`.

**The written trip-wire.** A capability MUST get its own name if any of: (1) different response *type* — it would need a parameter that changes what the tool returns rather than how it filters; (2) different consent class — read vs write vs spends brainz's money; (3) latency class differs >10× from the host tool's published promise; (4) hard external mandate; (5) the caller is not a model, and then it must be excluded from every advertised list; (6) the host verb would exceed **8 model-facing optional params** with nothing demotable to connection state or the envelope. Counter-rule: same response type, same consent class, same latency class, fits the budget → it is an argument, and continuing to argue is the drift. "Frozen forever" is replaced by two differently-enforced commitments: a **permanent semantic freeze** (a field named X never changes meaning or type; enum values frozen; `required→optional` safe, `optional→required` banned forever; never publish a schema you cannot honor forever) and **dated manifest releases** — `surface-2026-08`, ≤2/year, announced 90 days ahead, server serving both epochs simultaneously keyed on the approved digest so there is no flag day. Adopting the 8-param budget forces a cleanup on day one: gbrain's `recall` ships **10** — and `supersessions` ("return only the supersession audit log") is a mode switch, a second tool wearing recall's name, while `grep` is documented "Applied client-side after recall," pure surface tax. Cut both, land at 8, and `relation`/`depth` fit. The two-year test that both reviewers ran and the earlier lanes failed: **sharing a brain and mounting a team brain.** Granting a third party access to your memories is a new consent class and a deliberate human decision, so it is a web-app action, never a model action. *Reading* a second brain is connection state — one grant per brain, a second connector connection — never a `brain_id` param on five verbs. That answer costs zero schema changes and matches gbrain's own two-axis model.

### Rationale

The commissioning question was "why seven?" and the honest answer was "no reason." This card's number is a consequence: eight jobs, one wearing two names for disjoint audiences, one no model selects — nine on the wire, seven in front of any model. Change the jobs and the number moves, which is what makes it a rule rather than a target.

Three corrections do the real work. **The endpoint fix** turns per-client tailoring from a self-reported-header gamble into an install-time choice bound to an OAuth grant — the difference between a design that violates a hard external constraint when a header goes missing and one that cannot. **Cutting `synthesize`** is the only decision that changes brainz's cost structure: every remaining tool is SQL plus a sub-cent embedding on write, which is what makes a $10–20/mo consumer product possible, and the one exception is the exact shape that produced a documented 53× overrun in the reference codebase. **Moving the attestation into `_meta` on every response while keeping `brain` as its model-reachable rendering** is the card's best moment — it upgrades the trust claim from something a caller must think to request into a property of the connection, and it does so without betting the product's central promise on unproven virtual-document discovery.

The growth-channel answer matters most over years. "Ship capability as resources" was the old card's escape hatch and it is inert on half the target surface. Naming the envelope as the primary channel — closed at seven keys, request-independent, referentially checked — is the only strategy that grows on all four clients, and the connection-state rule is what keeps a parameter the model must supply identically 200 times from ever entering a schema.

### Downsides

- **`entity`'s latency promise collides with the substrate, and the fix is a restatement, not an engineering trick.** Per-user Neon with scale-to-zero takes seconds to accept its first query — on exactly the call an agent makes first. Keeping projects warm contradicts the near-zero-marginal-cost economics the whole design rests on. So: publish warm-p99 < 100ms plus a separate cold-start budget and a `cold_start: true` response field. That is a weaker promise than gbrain's, on the tool whose entire justification for having a name is the promise.
- **Cutting `synthesize` forfeits the demo.** "Ask it anything and it reasons over your whole life" pitches better than "it hands your agent the right evidence," and two of three independent lanes kept the verb. The mitigation — `briefing` + budget-packed `recall` should be indistinguishable in output quality since the caller's model writes the prose either way — is a claim to verify against real transcripts before any marketing page commits. It also means brainz fails gbrain's own certifier, and "memory-verbs-v1-partial" is a worse story than conformance.
- **`manage`'s invisibility is unresolved and the fallback is real cost, not a fix.** If hosts refuse to forward `tools/call` for unadvertised names, it becomes the eighth advertised tool on `/mcp` — ~700 tokens of prompt on every request, plus an entry in the model's selection space that always fails for the model. Safe, but the "no model sees more than seven" claim becomes eight, one of which is noise.
- **`recall(entity:)` and the `entity` tool overlap and I did not remove it.** One is a filter on ranked evidence, the other a card lookup — different response types, so both survive test (a) — but a model can still pick wrong. Descriptions disambiguate; nothing enforces it. This is a live instance of the overlapping-tools failure the card cites elsewhere.
- **Long-form capture inside `remember` is the weakest boundary call.** Document-level near-dup detection is a materially different algorithm from fact-level dedup, and `entity_slug`/`valid_until` are meaningless for a note. It passes the response-contract test on paper (`{id, status}` is genuinely shared) and the tripwire is written, but a reviewer called this already-tripped and the counter-argument is not airtight.
- **`briefing` is a bet on the batch pipeline.** It is SQL over pre-consolidated facts; if nightly consolidation is weak it is a worse `recall` with more tokens, and agents will learn to route around it. It should not ship before that pipeline is measurably good — which is doubly load-bearing now that it also absorbed `synthesize`'s job.
- **Two endpoints means two golden manifests, two conformance profiles, and a cross-surface-equivalence test that covers ranking and body equality but not authorization.** A scope check added to `fetch` and not to `recall({id})` is a cross-source leak the equivalence test will not catch. The auth check must live in shared dispatch, below both handlers — and nothing structural enforces that.
- **Whether OpenAI's connector review accepts a `/openai` surface carrying five tools beyond the mandated two is [unconfirmed].** No review-policy document surfaced. If a reviewer requires the compatibility pair alone, `entity`, `briefing`, `remember`, `forget` and `brain` must ride inside `fetch`'s id grammar on that endpoint — workable, materially worse, and a redesign of half the card.
- **The enterprise freeze is designed against conservatively because its granularity is unconfirmed.** I assume a description edit costs a re-scan, which prices the capability index at manifest-release granularity. If description edits turn out to be free, the design under-uses a cheap channel — a strictly safe error, but a real one.
- **The 8-param budget is a judgment call, not a measurement.** It is calibrated on one codebase's most-loaded verb, and gbrain's +13–17pp hierarchical-dispatch result was measured on markdown routing tables, not live `tools/list` selection. If the number is wrong it is probably too generous.

### Confidence

**76%** — high on the structure (the two derivation tests, the endpoint fix, the growth ladder, the trip-wire), lower on three specific calls. What would raise it: (1) an answer on whether hosts forward `tools/call` for unadvertised names — that single [unconfirmed] moves `manage` between "free" and "an eighth advertised tool"; (2) a measured cold-start distribution on per-user Neon, which decides whether `entity` keeps a latency promise worth naming a tool over; (3) one real ChatGPT connector review of a `/openai` endpoint carrying seven tools; (4) a month of instrumented traffic showing whether `brain` is actually reached when users ask privacy or inventory questions, or whether the model never thinks to call it. Verifying `briefing`-plus-`recall` output quality against transcripts a `synthesize` call would have produced would settle the loudest disagreement between the three lanes.

### Complexity

**High** — two endpoints with independently golden-filed manifests, a per-grant surface filter, a unified opaque-id grammar, `search`/`fetch` as pinned projections with a cross-surface-equivalence suite, a closed envelope with referential-integrity checking on `next[]`, a nonce-minting panel path, dual-epoch schema serving keyed on approved digest, and a nightly consolidation pipeline that `briefing` is entirely dependent on. The tool surface is small; almost nothing else here is.
